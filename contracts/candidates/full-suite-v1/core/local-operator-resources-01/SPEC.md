# Operator-selected local resource budgets

One narrow configuration contract implementing the owner's explicit request to let the operator choose limits and manage storage. It supersedes fixed operational ceilings for the opted-in local execution path. It does not relax financial correctness, accepted rights, record grammar or atomicity. No calibration or universal completion proof is required.

## Configuration and ownership

Extend the existing private `billing.json` installation object (`ledger-billing-installation/1`, store_id, scope) with one OPTIONAL `resources` object. Existing files without it retain legacy behavior. Do not add resources to commercial `billing_setup`, customer requests, Policy, Terms or accepted price data. The administrative surface is `workflow resources show` and `workflow resources set FILE`, where FILE contains the exact object shown in LOCAL-OPERATOR-RESOURCES-EXAMPLE.json. This is a trusted local-owner operation under existing filesystem ownership/privacy and writer exclusion, with atomic file replacement; no DB settings service or remote configuration API.

The object is closed, schema `ledger-local-resource-settings/1`, with all nine fields required. Each value is null or a positive canonical-JSON safe integer (maximum 9007199254740991); reject unknown/missing fields, booleans, floats, negative/zero values and integer conversion overflow. Null means no operator-imposed ceiling for that dimension, not a maximum-integer sentinel or unchecked arithmetic. u64 applies to work and attempt_timeout_ms (finite durations must safely convert to the platform monotonic deadline); allocation/size counts must convert safely to usize; retained counters must fit SQLite's existing signed integer representation. Actual allocator/OS/SQLite capacity, checked counter overflow and cancellation remain possible operational refusals.

Coupled E+W/L+W and byte equations use the selected operational thresholds; unrelated legacy record-format constraints remain. A mechanical schema migration must remove the fixed workflow-state/commit-sequence storage upper CHECKs that would otherwise silently retain the old quota. Preserve positive/nonnegative integer constraints, uniqueness, immutable-record triggers, identities and transaction rules. No deletion/pruning or INSERT IGNORE is introduced. Per-record accepted byte-format CHECKs are not storage quotas and stay.

## One effective attempt snapshot

Read and strictly validate the private installation configuration before constructing the local arena/session. Bind the immutable effective settings, store/scope and exact file identity to that same attempt. Confirm the captured configuration under the held writer before authoritative execution, and recheck before commit using existing currentness machinery. Never change a running attempt's allowance, reload a higher value mid-request, mint a second child, move debits to another attempt or switch to Noop. A changed configuration makes the attempt stale/refuse safely; the operator can retry under a newly captured setting.

The same typed core ResourceLimits travels through AuditArena, OriginalAuditSession, Meter, ResourceLedger, Records and actual member validation. Host passes only the validated operator snapshot, never a payload flag. Legacy constructors and non-opted-in recipes retain their existing fixed behavior. A settings reduction below existing retained usage is allowed as configuration, but blocks further growth until changed; it must not relabel retained data as corrupt or delete it. Read/status/retry may still need configured working resources, but lack of append quota must not by itself reject returning an already committed receipt.

Expose the effective settings and SHA256 of their canonical JSON in the existing administrative show response and captured CLI/demo status. This provenance is operational, not financial authority: do not add it to money IDs, request identity, accepted terms, receipt schemas or pricing inputs. Original retry returns the exact original receipt/result; a new operational setting neither rerates nor rewrites it. Current read rights and exact original intent still apply. Saved record bytes remain immutable.

## Metadata and constraints deliberately retained

One local operator-resource profile/amendment states that installation resource settings override the local operational quotas; numeric operator choices are not baked into the compiler, commercial policy or acceptance digest. The code-owned profile identifies the configuration semantics, not one operator's numbers. Update fixed local metadata claims once where they purport to prescribe operational runtime limits; do not keep claiming a finite worst-case completion guarantee for an unbounded setting. Do not create a fresh schema/profile per number change. Old experimental recipes and their original saved verification remain untouched; opted-in local use is an explicit operational amendment, not silent relabeling of old bytes.

Retain accepted-format/language restrictions: canonical JSON and schema/kind rules, lexical ID/Ref/time forms, per-kind representation/request/evidence limits, parser/depth safety, source document/field/rule/predicate/path cardinalities and other closed schema cardinalities. These must be reported honestly as format/language limits, not advertised as unlimited chains or arbitrary records. Retain exact arithmetic, money/scale/atom and integer-bit correctness bounds. Retain financial topology/impact limits of 32 affected decisions and 128 actions, original financial reservation/dependency set equality, exposure/funding ceilings and all monetary/authority/timing/claim/CAS predicates. The operator budget cannot waive them. None of these constraints is a universal future execution guarantee.

Existing errors should name the exhausted operational setting, configured value and actual observed/requested value in a sanitized CLI message; retain existing public error codes and commit-outcome semantics. If a retained format or financial limit refuses, identify that class explicitly rather than calling it an operator quota. No debugger, new receipt protocol or generic diagnostics framework is needed. A resource error after an uncertain commit is still unknown, never an asserted rollback.
