# PUB-RUNTIME-SEAMS-01 — authority, support and capacity amendment

Astra-authored candidate, 2026-10-12. Supersedes only conflicting authority/support/admission interpretations in PUB-ENC-01; its files, twelve synthetic envelopes and freeze hashes remain unchanged. Encoding acceptance is not runtime qualification. This amendment supplies implementation decisions; the shared capacity profile in §3 requires explicit owner acceptance because it is stricter than current separately metered legacy profiles. No financial formula, source permission or customer assent is changed.

## 1. Local administrative actor and retained authority

`LocalOwnerAdmin` is a private-field capability constructed only by a trusted **local entry point**, bound to the held `Owner` and verified installation identity. It is not deserializable, obtainable from request flags, a bearer source token, a retained snapshot, or merely the server's globally held lock. The local entry verifies the process's authority to open the installation/configuration and verifies the configured store/scope/operator mapping. A remote service holding Owner for every caller cannot supply this capability on behalf of those callers. Remote/delegated publication remains unsupported and fails `AUTHORITY_REQUIRED`; no existing `read`, `submit` or `correct` right implies `admin` or `policy.publish`.

Actual `Owner::acquire` checks exclusive OS lock and path identity, not directory UID/mode or remote caller authentication (`store/sqlite/owner.rs:12–87`). Accordingly `local-private-directory-owner/1` is a trusted local-process profile, not a claim of a checked POSIX directory-ownership credential. Implementations must not advertise remote authenticity or proof against the local administrator. No invented owner generation or secret snapshot is added.

Fresh publish derives store/scope/principal/source from verified installation Setup and its retained permission/configuration history under the coordinator locks. Principal is Setup.operator, source is the configured canonical source mapping, namespace is its trusted economic mapping, revision is actual effective source_grant_revision. Requested source/store/scope must equal those values. Missing, corrupt or ambiguous mapping refuses. Rights `[admin,read]` in LocalAuthorityBasis describe the local administrative actor, **not** a promotion of Setup.permissions. The revision records observed source configuration provenance only; it grants no administrative right. Source changes are not silently permitted by a new publication.

Local admin current read authority is held local actor capability plus current verified store/scope identity. It permits reading retained original publications/status from an earlier source mapping in that store/scope even after that mapping is no longer current. It does not require current source `read`, `submit`, `correct`, current compiler availability or current source mapping equality. A scope/store switch or absent local actor fails read. Fresh publish requires the current mapping above. Legacy source callers retain their current source-read rules and cannot acquire these owner-only reads. Removing legacy source `submit` blocks that source's legacy submissions, not owner publication; removing source `read` blocks source reads, not the administrator's access. This explicitly resolves PUB-ENC-01's ambiguous “current source grant” phrase; it is not a new delegated permission.

Original-key flow: authenticate current local read → load exact original OperationRecord and saved descriptor/evidence closure → normalize retry against retained original rules → compare original key/hash → return original receipt or identity conflict. Do not require fresh compiler or original write authority. A genuinely new operation then validates current mapping, trusted compiler support and sources outside the transaction, followed by locked **original-key lookup first** and revalidation of current local actor/configuration before append. A concurrent original wins over stale fresh assumptions. Status does not normalize/compile anew. No receipt rewrite on configuration/revision change.

Snapshot shape/hash remains PUB-ENC-01. LocalAuthoritySnapshot is generated only from this resolver and atomically retained; never accepted from inline source documents. On reopen, verify its exact body/hash, operation copy, membership and historical store/scope/principal/source equality; preserve historical authorization. Current read capability is separately required. An administrator cannot bootstrap actual customer assent, work authority or supplier offers by publishing. Those remain separate Wave2 obligations.

## 2. Binary-owned compiler support

Pure core exposes `compile_publication(sources, root, &VerifiedCompilerSupport)`. `VerifiedCompilerSupport` has private fields and no general public descriptor constructor/deserializer. The production `builtin()` factory is compiled alongside the implementation and constructs the descriptor from embedded immutable JSON artifacts in `runtime-support/`. It verifies catalog schema, constants and exact supported branches against its compiled implementation, canonicalizes each artifact, computes raw SHA256(JCS(body)) and constructs the existing CompilerDescriptor. No filesystem, environment, DB, network, source document or CLI setting chooses support. A library embedding can select only an explicitly implemented builtin profile, not supply an arbitrary descriptor as authority.

The source compiler document must exactly match the builtin descriptor's canonical body and Ref. All descriptor arrays are canonical sets; capability names are versions of closed implemented primitives. The descriptor is data identifying support, not executable code or trust merely because a retained digest matches. Saved historical operations remain readable with retained descriptors without pretending the current binary can compile/execute them. Fresh publication requires actual supported descriptor; unsupported capabilities fail before append.

`runtime-support/limits.json`, `mode-matrix.json`, `contract-profile.json` are exact digest bodies. Nothing is omitted when hashing. The contract profile binds exact reviewed encoding artifacts by raw file SHA256, avoiding a descriptor/self-hash cycle. These are **candidate production catalog inputs**, not a claim that the current released binary embeds/supports them. `descriptor-expected.json` is the author-derived expected descriptor/ref; independent reviewer reproduction is required before qualifying it. Binary/build provenance remains separately generated from the actual artifact, never copied from synthetic fixtures.

PUB-ENC-01 intentionally hashes three synthetic text strings. Its descriptor remains valid only in a private test fixture support constructor that matches that exact known fixture; the constructor must be test-only and unavailable to public runtime callers. Tests using it prove selected encoding/compilation, not production support. Production source discovery supplies the real builtin descriptor; a program must name that descriptor and therefore has new source/plan/publication hashes. Do not change the historical fixture to resemble production. A real-path fixture must separately test these catalogs, production factory and actual coordinator.

Initial subset in mode-matrix is compile/publication support only: component_workflow, retail base unit roots, required bounded nonnegative caller integers, true predicates, no basis/links/outcomes/stages/delayed costs/caps/shares/conversion. Unsupported forms reject, never truncate or claim all-mode support. Template role_slot and policy binding-slot name are distinct namespaces: do not require equal strings. Rule.binding_slot selects the policy slot; component book must agree. Actual role and funding authority are acceptance obligations. Optional Activity.funding_leg absent adds no restriction/default; when present it must equal the selected priced slot's funding_leg. Every rule's quantity unit must exactly match its field unit and a terminal declared unit.

Static money proof uses exact integer arithmetic: unit-rate atoms times quantity maximum, then sums **all simultaneously reachable positive roots per activity/book/binding_slot** (and the activity/book total across slots) with checked addition. Every individual and aggregate bound must fit MAX_ATOMS=10^30−1. Example two roots each 600000000000 units at $1 have 6×10^29 atoms each but 1.2×10^30 total: reject before publishing. This is static representability, not accepted exposure or customer authorization. Fixed worst_case constants do not replace proof. All current dynamic funding/exposure/correction guards remain required before execution.

## 3. Proposed shared installation admission profile (owner gate)

Actual baseline M3 counts entries/aliases and bytes across three table generations (`store/sqlite/billing.rs:264–288`). M5 separately counts records+commands+activity identities and canonical/identity bytes (`store/sqlite/m5.rs:2561–2605,2662–2687`). P2 workflow independently counts operations and payload bytes. These separately available ceilings must not be called one already enforced installation budget.

Proposed `workflow-shared-capacity/1` conservatively shares existing numerical ceilings without increasing them. Its units are **capacity units**, not accepted decisions. Let E=M3 verified entry_count; A=M3 alias_count; EB=M3 entry_bytes; AB=M3 alias_bytes; R=M5 record_count; C=M5 next_command_sequence−1; I=M5 activity_identity_count; MB=M5 canonical_bytes+activity_identity_bytes; W=workflow operation rows; WB=workflow payload meter defined below. Admission requires E+R+C+I+W ≤100000; EB+MB+WB ≤268435456; A ≤100000 and AB ≤67108864. All original sublimits, permission-change bounds, transaction/doc limits and M5 boundary ceiling remain. No million-record profile and no reserved-capacity/performance guarantee.

WB is SUM byte lengths of workflow_documents.canonical_bytes **once per unique stored document row**, plus for every workflow_operations row length(identity_key)+length(operation_bytes)+length(manifest_bytes)+length(receipt_bytes). The existing P2 identity column spelling must be mapped to this identity_key semantic field; its canonical key bytes are charged once. Original request bytes embedded as base64 in the operation count through actual operation bytes. If a future authoritative table retains another payload copy, its actual bytes require a declared meter addition before that writer is enabled. Derived indexes, SQLite page overhead, WAL and reconstructible projections are not payload bytes; no physical disk bound is claimed.

Fresh operation delta units1; byte delta exact new operation/key/manifest/receipt bytes plus only new unique document rows. Canonical compare existing document identity/content before computing new-row delta under the same transaction lock. Reusing source/plan/publication docs contributes zero new doc bytes. A new authority snapshot counts if new. Same original-key retry appends nothing: all deltas0. New-key semantic alias is an administrative operation: unit1 and its actual bytes; it does not use the free remainder of another ledger/alias budget. It is not an economic decision. Reject duplicate supplied source refs before mapping/coalescing; a referenced reused stored doc is different from duplicate entries in the request.

Before enabling this profile, recompute/verify all legacy and workflow meters from retained rows. If the sum already exceeds a shared ceiling, refuse **workflow enable/new admissions** with an explicit capacity diagnostic; do not call valid legacy history corrupt, erase/reset counters, delete history or silently raise the profile. Existing legacy-only mode remains available under its original rules until the owner chooses migration/capacity scope. Reads, original status/retry and integrity recovery remain available. Once enabled, every M3/M5/workflow mutation including legacy-compatible writers checks the shared meter under the same writer lock before commit; schema/profile fencing prevents an older writer bypass. Permission-only records retain existing separate bound; they cannot carry free workflow payloads. No enable claim until all writer hooks and migration fencing exist. Transactions update counters atomically, unknown commit is resolved by original status; never decrement on uncertain commit.

This conservative sum can refuse a composition that fit separate legacy meters. That is a disclosed compatibility choice requiring Steve's approval before activation. Alternative accepted-decision aggregation needs a separately defined M5 classification/projection and reviewed vectors, not a guessed record count. Pending decision, implement meter verification and report diagnostics but keep new public workflow mutation disabled; unaffected pure compiler/read/store-integrity work can continue.
