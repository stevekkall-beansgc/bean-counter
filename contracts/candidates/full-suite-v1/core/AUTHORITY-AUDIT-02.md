## 1. Exact trust and interpretation

`VerifiedAuthorityHead` is a private, nonserializable capability constructed by the store coordinator after the algorithm below. A request, retained observation, digest, SQL head/index, cached success, process holding an Owner lock, or synthetic fixture cannot construct it. The trusted inputs are an actual held single-writer StoreRoot, the entry point's authenticated actor, configured installation mode/custody, trusted coordinator time and the binary-owned verifier dispatcher. The existing explicit local-root custody assumption remains necessary: hashes cannot prove that an arbitrary copied/rehashed database was historically operated by the claimed administrator. Real-local and isolated-synthetic contexts cannot substitute for one another.

Pure core receives checked values from that capability, not SQLite handles or a caller `verified` flag. The capability contains actual store handle identity, read-snapshot identity, enrollment/head Ref and revision, exact current/original grant operands, audit commitment, verifier identity and observed time. Handle/snapshot identity are process-private and not a invented persisted owner generation. The serializable `AuthorityPrefixObservation` is evidence of what was audited; it has **no independent authorizing force**.

Fresh mutation uses `resolve_authority_head(held_root, authenticated_actor, enrollment_ref, original_grant_refs, observed_at)`. The enrollment determines the source, canonical economic namespace, customer ceiling and initial grant. Current source state is loaded from the actual checked head. The original grants are exact accepted-binding operands, not selected by the caller to widen authority. Current/original grant intersection, source-slot, terms, customer, operation, product/activity/link selectors, expiry and correction rights remain pure-core checks. Revocation is a valid auditable terminal state; a successful audit of it does not permit a new economic write.

## 2. Origin membership, introductions and audit order

An **origin** is a successfully committed operation triple `(OperationRecord, Manifest, Receipt)` with exact original OperationKey and commit_sequence. A document's origin is the earliest *validated introduction*, not the first row, first hash match or earliest manifest that happens to list it. A secondary origin index is only a hint. Duplicates under a different key never take ownership from that original introduction.

For a requested authority head the seed set is exactly `{enrollment_ref, current_state_ref} ∪ original_grant_refs`, plus current_grant_ref when active. Walk every actual Ref in each seed's body recursively, including prior_state_ref, original_ceiling_ref, source/customer/evidence/authority refs. The enrollment contains its ceiling by value; it is not a second independently created record. Stop only at an explicitly configured root-basis Ref whose exact body/mode/store/scope was authenticated under existing LocalOwnerAdmin custody; never stop because an arbitrary record says `root`, `verified` or `trusted`. The root-basis body and its expected Ref are included in exported audit evidence.

For each non-root Ref R, resolve its validated origin C. Include C's exact origin pointer and all three wrappers. Add **all members** of C's manifest to the walk, plus all actual Refs in C's normalized request, saved descriptor resolution, authority snapshot and receipt result. Implicit dependencies declared by C's original recipe are also mandatory (for example original AcceptedAgreement for agreement activation/stop, publication BuildManifest). A receipt's own operation/manifest links are checked as the same triple, not recursively treated as an earlier origin. A member introduced by C is a same-operation introduction; validate it inside C as below. A retained member not introduced by C must have a strictly earlier validated origin. This fixed-point set, deduplicated by exact Ref and OperationKey, is the pointer membership. Pointer order is numeric commit_sequence; equal sequence with different key, duplicate key with different wrappers, missing origin, future origin and cycles refuse. No incidental unrelated store commit belongs to this set.

The implementation must reconstruct earliest introductions from the authenticated retained workflow prefix; the origin index alone is insufficient. It must produce the same minimal pointer set above. The reference algorithm scans the installation's committed workflow operations in increasing commit_sequence up to the greatest required origin, validates each encountered origin once, and constructs a temporary introduction map. Sequences need not be contiguous because legacy commits may interleave; uniqueness and strict order are mandatory. It never treats a later successful alias as the lost original's introduction. An earlier observation is reproduced at its saved head Ref and saved original_grant_refs; current head is irrelevant to historical verification, but required separately for fresh authorization.

`ValidateOrigin(C, verified_earlier_prefix)` dispatches by the **saved registry digest, payload schema, normalization profile and closure profile**, through retained, binary-owned historical verifier code. It verifies raw/normalized request evidence, descriptor anchors, canonical bytes/IDs/digests/kinds/scope, exact original key, atomic triple cross-links, full declared manifest membership, result refs, authority derivation, introduction uniqueness and original operation semantics. It validates the original authorization at original trusted acceptance time; it does not reauthorize an old commit against today's grant. Saved plan/evaluator is used for economic origins; no current-policy rerating or current compiler regeneration.

Introduction recipes are closed: publication may introduce exactly validated inline source definitions, compiled plan, publication, actual build and authority snapshot plus wrappers; source-retention introduces the exact direct/fragment/finalized source and snapshot; AGR evidence/customer/enrollment operations introduce their exact input/derived records; agreement accept/activate/stop introduces permitted private documents and exact derived authority/intent/head/result records; ECON introduces exactly the fixed economic/evidence/state/capacity results of its pure evaluation. Already-retained bodies must match exactly. A document cannot gain provenance merely by appearing in a manifest. Same-operation references are legal only among that recipe's enumerated introductions, with its acyclic construction order and a checked complete manifest. Unknown recipe or unavailable old verifier returns `HISTORICAL_VERIFIER_UNAVAILABLE`; it is not a valid empty introduction set.

For source enrollment specifically: validate retained source-enrollment evidence/customer records under their original roots; recompute initial grant from the exact ceiling and initial state revision1. A restriction retains the same enrollment/namespace/principal, exact prior head, revision+1 and a subset grant; a revoke retains exact prior head and is terminal. Every original grant named by the observation must be introduced by this same lineage, before or at its saved head. This permits original broader terms to be retained but never widens the current grant. Same-operation initial enrollment/grant/state is checked as one introduction group, not a fictitious earlier grant operation.

## 3. Closed observation, verifier and hashes

`authority-audit.schema.json` supplies closed dictionaries. All set arrays use canonical JCS order except origin pointers, ordered numerically by commit_sequence. Counter strings are canonical nonnegative decimal. No null/default fields. The observation has exact source/head/original-grant seeds, root Ref, verifier Ref, origin pointers commitment, origin/document counts, audited retained-byte count and trusted observed_at. Current_grant_ref is absent exactly for revoked state. Counts are derived, not trusted budget claims. origin_count/document_count/audited_retained_bytes describe the minimal dependency witness (documents including the root once, each selected key and three wrappers once), not all prefix visits, total installation WB or a new commit charge. Runtime separately meters the complete verification-prefix scan. Audit pointer bodies are in the export package; the observation stores their digest/count, keeping future source histories out of individual economic bodies.

`prefix_digest = H_authority-origin-prefix([logical_store_id,scope,root_ref,enrollment_ref,current_state_ref,original_grant_refs,verifier_ref,ordered_origin_pointers])`.

Each pointer is `{commit_sequence,operation_key,operation_ref,manifest_ref,receipt_ref}`. No mere unverified hash or new signature. Observation and verifier use the existing document domain `H_workflow-document([schema,body])`, ID `wdoc_` plus digest hex, kinds `workflow-authority-prefix-observation` and `workflow-authority-audit-verifier`. The verifier document is code-owned metadata, not an executable plan/plugin. It pins raw SHA256 of exact contract artifacts and the supported original registry/profile recipes; path strings are relative public contract paths, never local absolute paths or environment values. Binary support checks exact descriptor Ref/body against its built-in dispatcher. An installed binary must retain every verifier needed by its accepted unresolved obligations before upgrade; removal is an incompatible upgrade and must refuse activation, not erase old correction rights. Keeping a descriptor file while removing the code is insufficient.

The selected fixture verifier is **synthetic supported metadata in an explicit synthetic harness**. Its artifact hashes are real hashes of candidate contract files; this does not claim any production binary implements them. Actual build provenance is a separate PUB-BUILD-01 fact. No fixture descriptor may become a runtime trust fallback.

## 4. Separate audit resource contract

The audit is store-coordinator work, separate from economic4096-ref/8MiB/65536-visit evaluation. Its admissible input is the existing Profile-B workflow partition: at most100000 distinct committed workflow operations and at most268435456 charged workflow bytes WB. Audit counters recompute unique canonical document-body bytes plus every OperationKey/operation/manifest/receipt byte using the existing WB recipe; they do not trust a mutable meter or double-count reusable documents. The original E/L/EB/MB plus workflow equations remain unchanged. An installation violating B is an integrity/admission issue, not permission to drop history. No million-event claim.

Use a read snapshot and bounded scratch inventory. Read each unique canonical body/wrapper once into a verified byte spool; parse/canonical-check/hash once, memoize exact Ref and byte offset. Subsequent accesses use checked offsets. Spool maximum is WB; index/worklist/sort temporary storage is bounded by `16*WB + 4096*W` bytes, at most4,704,567,296. This is ephemeral local scratch, not a new authoritative database. Its rows never survive as trusted evidence. The factor16 permits fixed256-byte index entries because every schema-admitted retained document is at least16 canonical bytes; check that minimum as part of schema/catalog qualification. W wrapper indices have separate4096-byte allowance. Input below16 bytes is invalid, not a new accepted-body limit.

Logical execution budgets are deterministic: canonical bytes scanned/hashed ≤WB once per representation; binary index comparisons ≤`32*(WB+W)` (at most32 binary-search levels for the above bounded inventory); source set inclusion uses sorted merge, not quadratic pairwise matching; original recipe semantic work ≤1048576 per origin, with the tighter original compiler/economic limits still enforced. Total charged semantic visits ≤104857600000 and index comparisons ≤8593134592. The audit meter increments **before** each semantic instruction/comparison; exhaustion returns `AUDIT_INTEGRITY_OR_PROFILE_FAILURE`, never a partial verified head. Repeated whole-history audits per request are not hidden in these bounds: each of at most5 coordinator attempts has its own audit, total maximum5 times these counts. No wall-time or throughput guarantee follows from these conservative bounds.

Memory is bounded by an explicitly metered64MiB audit arena, including parser/evaluator temporary allocations, plus fixed256KiB I/O buffer. Index/spool sorting uses pages in that arena; no unbounded heap map/recursive stack. Per-origin original resolved inputs remain≤8MiB and canonical record≤4MiB. Contract qualification must show each supported original verifier can process every legal input in that arena and in its stated work bound; an allocator failure is operational unavailability, never changed economic eligibility. **This is a required implementation proof, not established by source-only fixtures.** The reference fixture assembler does not measure production memory or work.

A later valid grant amendment cannot enlarge this audit beyond the same global W/WB envelope; no per-root new audit quota or future grant-update cap is imposed. That resource separation is why a previously accepted correction need not reserve an ever-growing historical disclosure bundle. Before enabling live obligations, the dispatcher must be qualified for the entire already-admitted profile and must retain old verifiers. Unsupported history or insufficient storage/resources blocks enablement/upgrade, not a retroactive correction expiry. Deterministic cancellation checks occur between each origin and after at most4096 charged visits; cancellation before economic commit leaves no new receipt or head. During/after COMMIT, preserve unknown outcome and recover the original key.

## 5. Cache, locks and reads

There is **no cross-operation trusted audit cache in profile1**. Within one audit, memoized verification belongs to the exact private StoreRoot handle and read snapshot. Reusing body bytes by hash is permissible only after exact bytes/kind/scope verification in that snapshot; memoized authority is never portable. A reopen, restore, new root handle, cancellation, head change or changed verifier dispatcher discards the capability. Scratch progress files are untrusted and may be deleted; resumed work re-audits. No store-head hash alone establishes an earlier verified prefix.

Fresh transaction order remains original-key lookup first, then existing ordered source/authority and agreement/chain/dependency locks. Under those locks compare actual StoreRoot handle/logical identity/mode, exact current head Ref/revision and relevant mutable customer/assent/slot heads against the audited snapshot; sample trusted current time and rerun rights/expiry/intersection. Changed relevant head invalidates the capability and restarts bounded audit; unrelated commits do not invalidate immutable verified bodies but all aggregate admission counters are reread. Max5 attempts, max3 lock expansions; return the existing retryable contention result if exhausted, not `AUTHORITY_REQUIRED` or permanent capacity refusal.

Original-key retry/status first performs current read authentication, then verifies saved original evidence/triple/origins with its pinned original verifier. It does not require current source write authority, current head, fresh compiler support or a new audit observation. A revoked source without current read gets read denial; an authorized administrator's existing separate read authority remains governed by PUB/AGR contracts. Damaged history gives integrity failure; valid revoked/expired current source gives current authorization denial only on a fresh write. Never conflate them.

The selected local profile has **no supported Setup.source replacement/rebinding transition**. Its actual Setup source equals the canonical economic namespace; credential alias registration/remapping is unsupported (AGR authority source-mapping contract). A test must not mutate SQL/config history or invent a Setup generation to simulate that transition. Setup permission revision changes are a different supported history: the P2 lane reports original-key recovery after revision2 removes permissions, freeze and reopen, with current LocalOwnerAdmin read authentication; that does not give a source caller a new read/write grant. A fresh key using the wrong actual source refuses. Report source-remap lifecycle as unsupported/not applicable in this profile; any future credential-alias family needs its own explicit reviewed contract. SourceState restriction/revocation remains a supported independent transition and still invalidates a fresh source capability.

## 7. Retention, export, restore and offline verification

Every accepted operation retains its original observations, all referenced verifier metadata and the full origin dependency closure. GC cannot remove audit-only edges while any original operation/right requires them. Export has a closed `AuthorityAuditPackage` header containing observation Ref, exact root Ref, exact origin pointer array, complete document envelopes and complete original operation/manifest/receipt envelopes, all canonical bytes, plus verifier artifact inventory. Arrays are sets except ordered pointers. No body or pointer can be omitted because it is locally cached. Package chunks may use existing bounded read transport; the full package is a history export up to the audit bounds, **not** an8MiB single operation response.

Offline verification requires an independently supplied existing installation trust context pinning logical root/mode/custody and permitted historical verifier code, **and the complete authenticated retained workflow prefix** used to reconstruct earliest introductions. The selected package carries the minimal dependency witness; it is not evidence that an unrelated earlier introduction was absent. The prefix is obtained from the verified restored StoreRoot/checkpoint through the existing full-retention export, not an assertion embedded in this package. No new unreviewed prefix certificate or signature substitutes for it. The package cannot supply its own trusted root merely by including root_ref. Without that context and verified prefix a tool may report `HASHES_VALID_AUTHORITY_UNVERIFIED`, never authorized or economically verified. With it, reconstruct original introductions and pointer membership, re-audit, reproduce prefix_digest and observation bytes (including saved observed_at), and then evaluate the immediate economic bundle under original terms. A package with missing/changed/extra claimed pointers, wrong custody/mode or absent old verifier refuses authority qualification. Observation-only export is explicitly incomplete.

Restore stages full retained closure, verifies original receipt/origin chains and Profile B accounting, re-audits with retained original verifiers, then activates under the existing exclusive-writer/custody transition. Old and restored handles never share private capabilities. A successor may assume existing external authority only through the financial recovery amendment's explicit verified custody handoff; root strings or copied database files cannot grant it. Current source-head checks after restore use restored verified heads, while old observations are historical as-of evidence. Export and audit add no external signer assumption.
