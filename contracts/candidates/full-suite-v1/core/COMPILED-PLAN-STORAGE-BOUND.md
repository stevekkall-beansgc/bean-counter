# PUB-SIZE-01 — compiled-plan storage compatibility repair (candidate)

Astra author, 2026-10-13. Additive clarification for the original S12 §6/CORE bounded canonical encoder, publication-boundary.md §§1–3 and the unchanged builtin `runtime-support/limits.json`. Independent counterexample and implementation review required. No prior PUB-ENC-01/PUB-BUILD-01/AGR-ENC-03 bytes, digest catalogs or financial/authority rules are amended by this file.

## Finding and chosen repair

Sol's actual builtin compiler at implementation checkpoint `02ee1dc` accepts the supplied 21-document current-program source closure: 772589 canonical source bytes, 1088 fact slots, 128 alias-heavy component slots and 64 unit rules. Its resulting canonical CompiledPlan body is **1089536 bytes**, digest `sha256:6c6508e583dd93db69512f20f5e0e1e59f23827ea5403b2d1d2d12c73a9b97f0`. The recorded production run and mechanical count are evidence of a cross-layer defect, not independent expected output. SQLite `workflow_documents.canonical_bytes` currently applies1048576 to every kind, so the valid expanded IR cannot be retained. A1MiB source closure does not imply a1MiB compiled plan because the IR repeats resolved field/template/rule information.

**Chosen technical compatibility repair:** treat `workflow-compiled-plan` as a derived canonical record with a4194304-byte canonical **body** ceiling, consistent with the existing canonical encoder/plan `worst_case.bytes` and `canonical_decision_bytes` ceiling. Apply this per-kind value in store insertion, read/replay/retained validation, migration CHECK and coordinator admission. Keep the existing ≤1048576 storage guard for other document kinds, plus their existing stricter semantic source/authority/build limits. Do not raise any other byte limit. A plan beyond4194304 is rejected by pure compilation/prepare with `PROGRAM_BUDGET_EXCEEDED`, before publication or any durable write. Core's checked canonical encoder must reject that size even if every source/table count passed; a static count ceiling alone is not proof of byte size.

This is a storage acceptance repair within an already supported derived-record ceiling. It preserves the compiler-valid concrete counterexample and imposes no new source/cardinality/financial limit. It does **not** assert that every syntactically legal maximal source composition necessarily fits4MiB; existing aggregate byte/work bounds still decide admission. If an implementation currently emits a plan larger than4MiB, that is an existing canonical-record bound violation, not authorization for a larger profile. No owner choice is required to align the store with this existing ceiling; a proposal above4MiB would require a separate limit amendment.

## Exact byte domains and unchanged accounting

The4194304 bound is `len(JCS(CompiledPlan body))` in UTF-8, excluding Ref, transport envelope and LF. SQL canonical_bytes stores that same body. Plan ID/digest remain `H_workflow-plan(body)`, with unchanged framing. Ref/envelope bytes count wherever physically retained under the existing ProfileB and resolved-input meters; they are not smuggled into a larger encoder setting. Use bounded envelope streaming/response construction within the existing8MiB aggregate read/response limit if a wrapper adds overhead to a body at the boundary; do not pass a>4MiB wrapped value through an encoder whose own bound is4MiB and then claim successful encoding.

Source documents each≤262144 and source closure≤1048576 stay unchanged. Authority≤65536 and existing build inventory/manifest limits stay unchanged. Resolved operation closure≤8388608, manifest≤4194304, existing receipt bound and operation/transaction aggregate bounds all stay unchanged. Full publication can still refuse on one of these independent bounds even when its plan fits; return the specific existing budget error and commit nothing.

ProfileB is owner-approved. Charge actual unique plan bytes to WB once on insertion; reuse adds0planbytes, retry adds0total, alias charges its actual new wrappers and any truly new verification records. E+W≤100000, L+W≤100000, EB+WB≤268435456, MB+WB≤268435456 and all legacy subgates remain. There is no plan-byte exemption, extra pool, reset or hidden eviction. A store nearly full may correctly refuse this valid large plan for aggregate capacity.
