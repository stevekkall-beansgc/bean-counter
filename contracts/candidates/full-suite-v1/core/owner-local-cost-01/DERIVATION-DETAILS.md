# Fixture output conventions (additive derivation detail)

INPUT bytes remain those in the INPUT-first handoff. The initial SPEC is preserved externally; its connected-closure completeness revision changes metadata only and leaves this body/math derivation unchanged. This file fixes only deterministic fixture output construction, not runtime semantics or authority.

1. Resolve ordered `records`. `identity.type=document`: H_workflow-document([schema,body]), wdoc_. `type=record`: resolve tuple first, derive id=prefix+H_domain(tuple), then substitute body $self_id and hash workflow-record([kind,fixture.scope,body]). Named set_paths are sorted by JCS bytes. All synthetic fixture keys are ASCII, so this is equivalent to required UTF-16 key ordering. A Ref is {kind,id,digest:"sha256:"+hex}. `raw_sha` is plain hex SHA256(JCS(body)). Preserve array order unless set_paths explicitly names a set.
2. Resolve finalize_template and context. For each conditional case copy resolved final_line, verification, context; apply its patches. Recompute assertion Ref/raw SHA/digest, replace verification's corresponding fields, replace subject_binding_refs with its exact four actual assertion subject refs, sort JCS, derive verification Ref. Apply the complete SPEC conjunction against the unchanged expected context fields. Schema-invalid assertions also refuse. Output case name/result/assertion Ref/verification Ref; this demonstrates rehashing cannot repair a semantic mismatch. No error-order claim.
3. For each money_history, convert decimal service/markup to exact scale18 atoms. Use exact rational percent and multiplier, signed nearest ties-away once per result. Output premium, discount (negative), retail pass-through initial/replacement, supplier initial/replacement; stage totals `initial`, `outcome_corrected`, `cost_corrected`, with separate retail/supplier books. Output outcome correction actions [-premium,discount], cost supplier actions [-initial_supplier,corrected_supplier], retail cost actions [-old_passthrough,new_passthrough]. Do not net away individual actions.
4. High-water traces start empty claim→high-water map. Proposed new H=max(previous H,eligible) for the named permanent claim, new consumed=sum proposed map+other_consumed, new held=authorized−new_consumed−released. Accept iff eligible>=0 and new held>=0 (other full authority conditions are out of scope of this arithmetic-only trace). On refusal retain EXACT prior map/consumed/held/released; no new consumption record. Output each proposed amount, accepted flag, delta only if accepted, resulting complete map/consumed/held/released. Repeat equal amount and zero are accepted zero-delta transitions; they never restore held.

Its ID is wcostconsumption_ H_workflow-cost-consumption([derived cost_claim.id,"1"]); record digest as above. This is one byte/identity vector; later trace rows are arithmetic vectors, not a fabricated complete authenticated cost history.
6. Identity variants derive CostClaim ID from base line-key tuple with key_patch when present; nonidentity_changes are deliberately excluded. Output ID and same_as_original. A changed key is a different mathematical ID, NOT proof an account can be re-enrolled or a second claim admitted. The original component and owner-wide account/line constraints still apply.

The changed-basis schema must refuse. The changed-account also requires full new offer/owner/assent joins in reality; this vector proves the digest dependency only. Neither is an authorized accepted agreement.
