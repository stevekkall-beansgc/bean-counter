# Financial closure9 verifier dictionary consistency repair

This separate additive package implements the already approved commitment-first financial `/9` metadata association. It changes no financial semantics, authority, trust, history cut, resource rate/limit, source normalization, assent or operation registry. It supplies no production verifier body, capability, support factory, compiled plan or executable qualification. Old frozen files, bodies, IDs, descriptor digests and original dispatch remain immutable.

## Exact dictionary delta

`financial-verifier9.schema.json` copies the transitive local-reference closure of `economic-constructor-04.schema.json/$defs/AuditVerifier`: AuditVerifier, OriginRecipe, Artifact and Digest. Only OriginRecipe.properties.closure_profile.enum gains `ledger-economic-resolved-inputs/9`. Every other definition value is identical. Wire schema remains `ledger-authority-audit-verifier/2`; profiles, algorithm, resource string, six OriginRecipe fields, variant enum, Artifact grammar and both 1..64 unique-set bounds remain unchanged. No `/4`–`/8` catch-all is added. Schema `$id` and title describe this new packaging identity; the top-level AuditVerifier selection is unchanged. `schema-delta.json` states the sole definition delta; provenance identifies every copied definition. This repeats the precise additive-repair pattern in ECON-CONSTRUCTOR-04-BOUNDARY §4 for closure3.

## Registered tuples and prerequisite originals

`registered-financial-tuples.json` binds the thirteen literal payload/kind rows of the already frozen commitment-first registry whose saved closure is `/9`. Its registry digest is SHA256 of canonical JCS registry bytes, prefixed `sha256:`; it is not a raw file hash. Every such OriginRecipe uses normalization2, closure9 and variant `all`. Each row also records the exact original recipe_id, Descriptor6 and saved authority7/operation9/manifest9/source-audit1/financial-audit1 association from `dispatch.json`. These rows are registered vocabulary, not an assertion that any runtime implements them. No row may enter an advertised production catalog until its actual original verifier is implemented and qualified. Retained original obligations remain mandatory; omission cannot silently waive their support.

Financial history includes its real prerequisite originals. A code-owned catalog must separately describe all actually supported source, customer, definition-retention, publication, party, acceptance and activation recipes reached by that history. Use each original's saved registry/request/descriptors and exact old dictionary, not current registry762 by schema, union-schema aliases or a latest fallback. Existing AuthorityChange action-discriminated source/customer schemas retain their exact variant under AUTH-AUDIT-04. Non-discriminated party-authorize and party-revoke have separate literal payload schemas and no `action`; existing variant `all` describes each complete schema. These distinctions change no variant enum.

For a management recipe with no economic closure field, the verifier's closure_profile names its actual publication/agreement/source manifest recipe. The registry's saved-recipe sentinel `absent` is not an OriginRecipe enum value. Actual saved wrapper/manifest, normalized request/schema, descriptor and registry associations must all agree. New financial Descriptor6 is distinct from management Descriptor7 and from a verifier2 metadata document; none substitutes for another.

## New dictionary selection and unchanged original dispatch

A new code-owned production verifier catalog, when actually implemented and qualified, may select this dictionary only through its new exact descriptor body/Ref and artifact binding. The financial body profile is `ledger-financial-origin-audit/1`; algorithm remains `verified-introduction-fixed-point/1` and resources remains `workflow-profile-b-origin-audit/1`. Its complete artifact and origin-recipe sets must equal the binary's selected literal supported catalog. There is no caller catalog, inferred fixture support, schema-only support decision or authority from a retained descriptor alone.

Old verifier bodies continue to be checked with their original exact descriptor/dictionary and retained executable semantics. Do not mutate the old schema in place, accept /9 through the old /3 closed validator, reinterpret an old descriptor digest, or retry failed old-body validation against this dictionary. This package does not automatically revise any existing compiler/support descriptor or registry identity. A subsequently constructed support descriptor must accurately bind the new catalog/dictionary if used; original saved compiler/publication identities remain unchanged. Retaining a descriptor without its old executable verifier is insufficient (AUTH-AUDIT-02 §3).

## Artifact mapping and validation

Artifact entries remain `{path,sha256}`: a relative public contract path and lowercase 64-hex RAW SHA256 of those exact file bytes. They are not JCS digests, absolute development paths, environment values or executable plugin locations. Existing path semantics and grammar remain unchanged. The new catalog must bind this dictionary and the exact defining contract/schema/registry/profile/dispatch assets of its implemented recipes, including their required inherited definitions and original-audit/resource rules. `source-pins.json` provides reviewer provenance for this repair; it is not a ready-made production Artifact list. In particular, do not copy fixture input/output/checkers or the synthetic three-recipe/seven-artifact catalog as a production support declaration.

AUTH-AUDIT-03 §5 expressly confines that synthetic inventory to its harness. Production catalog construction must derive its exact artifact set from the real built-in dispatcher and stay inside the unchanged 64-entry bounds. This package deliberately does not invent a universal artifact list or declare all registered recipes implemented. Schema validity and registered-tuple matching are prerequisites, not original semantic verification, complete prefix/custody/currentness, source/financial witness membership, capacity or whole-resource qualification.

## Review evidence and limits

`check_dictionary.py` performs only JSON Schema meta-validation, exact four-definition reachability/equality, single-delta checks, exact registered row correspondence, and old-reject/new-accept checks for the thirteen OriginRecipe tuples. It creates no synthetic production verifier body. Its raw-hash checks bind source provenance. `check-result.json` is author evidence, not independent sealing. Root must independently review and seal this separate package before implementation relies on it. No runtime/build/calibration campaign or product-code change is part of this repair.
