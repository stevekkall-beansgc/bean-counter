# M2 implementation design

This design implements the customer and agreement scope in [the canonical billing roadmap](billing-roadmap.md). It keeps one business per installation and adds customer/source partitions inside that business. Multi-business tenancy and hosted infrastructure remain deferred.

## Identity and isolation

- A customer is an installation-local identifier. Each registered `(customer, source)` pair has its own operator-configured authority and agreement timeline. A customer may have more than one source; a source may serve more than one customer. Each customer has one canonical customer scope shared across its sources.
- Delivery, semantic, and control-command identities are scoped by `(source, customer)`. SQLite keys and alias checks use both values.
- Existing v0.4.3 records keep their original canonical scope and bytes. The first customer of a new schema-9 installation also uses the installation scope. Every other customer scope is `tenant = installation tenant`, `environment = "bc-customer-" + lowercase_hex(SHA256(canonical_json(["bean-counter.customer-scope", 1, [installation_tenant, installation_environment], customer_id])))`. The resulting scope is stored once per customer and checked on every open. Registration refuses equality with the installation scope or any existing customer scope. Additional sources for an existing customer reuse that customer's stored scope; setup input can never override it. This gives different customers separate event, chain, receipt, target, and economic-record IDs without changing the frozen core identity algorithm.
- Customer/source is required on each write command and is cross-checked against the request and registered profile. Statements and exports require a customer and cover all of that customer's sources; they refuse rather than return a partial statement if any source lacks read authority. Explain also requires a customer and never reports whether a target exists outside that customer.
- A request-intake operation is not implemented. `accept` records a separately submitted billable-work event; accepting a request, if added later, must not create a posting.

## Agreement records and time selection

- A `(customer, source)` timeline is append-only. `start` adds version 1, `amend` adds the next version of the same agreement, and `end` adds a terminal transition. A new agreement may start after an end. Every control request has a stable `change_id`, exact-retry behavior, and an expected revision. The change ID is unique across agreement and permission control operations for that customer/source; same-ID reuse with a different operation or bytes conflicts.
- Start/amend inputs carry a complete validated terms setup plus an explicit `effective_at`. Installation scope, store ID, host and operator must match the immutable business setup. Customer/source identify the registration. The first setup for a source establishes its permission ceiling; amendments must preserve it exactly. Only agreement, binding, price, assent and outcome terms may change. End inputs carry the customer, source, agreement, expected revision, effective time, stable ID, and reason. Customer/source data permissions authorize billing operations; local private-filesystem administration authorizes registration and agreement control. Assent time remains separate from effective time.
- New controls retain both `recorded_at` (the ledger time sampled after acquiring the serialized writer transaction) and `effective_at`. New start/amend/end controls refuse retroactive effective times (`effective_at < recorded_at`); the migrated v0.4.3 initial agreement is the sole historical exception. This prevents later controls from changing which version an already accepted event resolves to. A source/customer timeline requires effective times in nondecreasing order; only an end followed by a new start may share an exact boundary time, in serialized revision order. At any work-acceptance time there is either one active agreement or none.
- The writer begins its serialized SQLite transaction before sampling the ledger clock. New economic and control writes refuse if the clock is earlier than the maximum retained economic/control ledger time; equal microsecond timestamps are allowed. Only after scope and current read permission are checked and an exact delivery or semantic retry has been resolved does a new billable event select the agreement active at that timestamp. Caller `occurred_at` remains evidence and never selects price. The selected agreement ID/version is retained in the entry metadata and validated against its immutable terms and acceptance timestamp, without changing frozen canonical record bytes.
- Exact delivery/semantic retries are resolved before current effective terms, but only after current customer/source scope and read authority pass. They return the original result across amendments and ending. A new semantic alias still resolves to the original accepted price. Outcomes and corrections use the target's original terms/policy and current customer/source authority; the request source must match the target source. Submit/correct revocation does not turn an authorized read-and-exact retry into new work.
- Agreement amendments cannot reset customer/source permission ceilings. Permission updates are append-only, customer/source-scoped control records with their own stable identities. Control retries are resolved before stale-revision checks; ID reuse across agreement and permission controls conflicts. Local permission status remains available to the filesystem administrator to reconcile an unknown permission-change result even after read revocation.

## Storage transition

- M2 introduces ordinary billing SQLite schema 9. A new store is created directly at schema 9. Existing schema-8 installations require an explicit `billing upgrade` command; ordinary M2 opens and writes never silently migrate a store.
- Migration 0009 preserves the schema-8 setup blob and every pre-existing entry, alias, permission row, record bundle, receipt, and external identity byte-for-byte. It associates those rows with the legacy customer and source, records the original scope, and creates agreement version 1 from the existing setup. The first migrated customer's scope remains unchanged. Legacy event/outcome/correction retries continue to compare their original `/1` ingress bytes when the caller supplies the explicit customer/source scope. Old `/1` permission-change retries resolve against the migrated expected revision and exact saved bytes; new control writes require their `/2` shape and stable ID.
- The transition acquires the same exclusive installation owner lock as ordinary writers, verifies the open-but-dispatch-held local billing profile, store identity, schema version/checksums and database integrity, then commits schema, checksum history and customer/identity mappings in one SQLite transaction. Before commit, interruption rolls back and the schema-8 backup remains usable. An unknown result is reconciled by reopening and checking the actual schema; retry only after confirming schema 8, and treat schema 9 as already upgraded. Migration refuses unsupported version/checksum/store-identity states before mutation. A release can enable schema-9 writes only after exact v0.4.3 schema-8 migration, failure/interruption rollback, old-writer refusal-before-mutation, row/receipt reconciliation, and pre-migration backup restore are qualified. The existing quiescent whole-installation recovery procedure remains the backup boundary.
- M2 retains the existing global 1,000-entry, 1,000-alias, 1,000-permission-change, 32 MiB economic, and 32 MiB alias-ingress ceilings. Customer/agreement/control storage receives explicit bounds; M3 owns any higher-throughput claim.

## Versioned command families

- Existing setup `/1` remains the first-customer setup and migration format.
- New customer/source registration wraps a `/1` setup with an explicit start time and stable change ID. Immutable business identity fields must match the existing installation; adding a source for an existing customer reuses the stored customer scope and cannot replace the source permission ceiling.
- Agreement amend/end, permission updates, outcomes, corrections, statements, and CLI command shapes use new `/2` family boundaries where their customer scope or semantics change. Each changed family is listed independently in the v0.5 compatibility record.
- Statement output identifies the customer and all agreement versions represented by its entries. Its cutoff and digest cover that customer's complete retained history only; entries and CSV rows use customer-local projection ordinals rather than global ledger ordinals. Cross-source adjustments are refused even if the target belongs to the same customer.

## M2 exit evidence

In addition to the storage transition, M2 must demonstrate two customers reusing the same source, delivery ID, and operation ID with separate histories; scoped exact/semantic retries and conflicts; missing/wrong/unauthorized customer refusal without disclosure or mutation; agreement start/amend/end boundaries chosen by monotonic ledger acceptance time; old-price retry and target-policy outcome/correction after change/end; customer-complete statements and exports; scoped permission revocation and restart; and unknown-commit recovery for work and control changes. Unsupported request-intake commands refuse without mutation; documentation identifies `accept` as billable-work submission and does not imply that request intake exists.
