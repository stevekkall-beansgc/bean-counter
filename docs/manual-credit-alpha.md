# Manual credit — local alpha tester guide

This is a bounded, unpublished alpha interface for synthetic local testing. It records an explicit negative USD credit against one named completed Work, its Stage and original retail Actions. It does not change or reverse those original Actions, calculate a correction, authorize a supplier payment, collect money, or produce a tax or legal invoice. Automatic Stage quantity correction remains deferred.

Use the private installation owner and a fresh synthetic installation. A customer needs the applicable existing billing and workflow setup; do not edit database tables to create authority or history. The original completed Work and Stage must be linked to the exact positive original retail Actions. The current local owner, customer, scope, original records, payer, recipient and producer evidence are checked by the ledger. The operator enters the amount and reason; the amount is not calculated or capped against the original charge by this feature. Distinct adjustment IDs are distinct credits, even if they reference the same original Actions. Exercise care with synthetic-only data during alpha testing.

The [alpha request schema](../contracts/candidates/manual-credit-m5/alpha/requests.schema.json) lists the exact closed fields for issue, status and read. It is a structural precheck, not a complete validator: it cannot enforce UTF-8 byte lengths, canonical ordering of Action references, authority, or semantic joins. `amount` is a negative nonzero signed decimal atom string in USD at scale 18, with at most 30 magnitude digits. Supply full references obtained from the actual retained workflow; do not invent their IDs or digests. Action refs must be unique and sorted by their canonical JSON bytes.

Given a reviewed JSON request file containing `ledger-billing-manual-credit/1`, issue it once with:

```sh
ledger billing --directory DIR adjustment credit REQUEST.json --json
```

The committed result has schema `ledger-billing-manual-credit-result/1` and fields `status`, `credit_ref`, and `record`; `status` is `committed`. Preserve the exact request bytes, selected customer, scope and adjustment ID. To check an uncertain result, use `ledger billing --directory DIR adjustment status SELECTOR.json --json` with schema `ledger-billing-manual-credit-status/1`, the same customer, `workflow_scope` and `adjustment_id`. A `ledger-billing-manual-credit-status-result/1` reports `not_observed` or `committed` and repeats the selector fields; a committed status also includes the original `result` and `request_bytes_sha256`. Do not assume an uncertain outcome rolled back. The exact-retry and changed-request conflict behavior has not yet been qualified for this alpha, so this guide does not instruct a replay.

Read a retained credit with `ledger billing --directory DIR adjustment read SELECTOR.json --json`, using schema `ledger-billing-manual-credit-read/1`, the same customer and scope, and the exact `credit_ref` from the committed result. Its `ledger-billing-manual-credit-read-result/1` contains `credit_ref`, `record`, `body_bytes`, `canonical_bytes_base64`, and `canonical_bytes_sha256`. The read does not create a presentation.

A separate ad hoc statement can present an unclaimed credit using `ledger-billing-ad-hoc-statement/3`: supply `customer`, a new `command_id`, `workflow_scope`, `adjustments`, `workflow_actions`, and `manual_credits` containing exact credit refs. Empty lists are explicit where appropriate. It is a separate immutable presentation; the original statement is not rewritten. The runtime is designed to prevent a credit being presented twice, but the competing-presentation refusal has not yet been qualified on this alpha. Do not submit a competing presentation as part of ordinary testing. `billing.statement` can read a saved statement by its customer and hash. This is not a complete statement, payment, or finance-export guide.

Manual-credit creation, presentation and read recovery have passed a bounded fresh synthetic journey on an earlier candidate; this does not qualify a later binary. Version-matched source, local gates and native artifacts must be checked independently. Back up the complete quiescent installation before any upgrade; schema 21 is not readable by the older v0.11 executable. No hosted authentication, remote authority, multi-host storage or resource-completion guarantee is implied.
