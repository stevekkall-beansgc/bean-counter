# M5 CLI and storage contracts

**Status (2026-09-29): Package 3 frozen after independent Sol and Astra reviews; not implemented.** The [billing roadmap](billing-roadmap.md) is canonical, the [decision register](m5-decision-register.md) records owner policy, and the [architecture baseline](m5-architecture.md) defines the system boundaries. This frozen contract specifies versioned M5 inputs, outputs, identity scope, exact period allocation, migration, and failure semantics. It does not amend `ledger-canonical-v1`.

## 1. Command families

All M5 JSON requests use strict UTF-8 JSON, reject duplicate keys and unknown fields, and carry an exact `schema` discriminator. Persist the exact accepted input bytes for retries. Timestamps use the existing billing `Timestamp` grammar: explicit offset, valid Gregorian instant, at most six fractional digits; normalize accepted values to UTC microseconds. Revisions and unbounded quantities use canonical nonnegative/positive decimal strings where the existing billing interface already uses string integers; signed integers exclude `-0`. Identifier limits follow M2 UTF-8 byte lengths, not Unicode character counts: customer and general IDs 128 bytes, source 256 bytes; control characters are rejected. JSON Schema `maxLength` is only an early structural bound, and service validation must enforce the byte limit.

| CLI operation | Request family | Identity domain | Durable result |
|---|---|---|---|
| `billing term set` | `ledger-billing-term/1` | `(customer-admin, customer, change_id)` | Immutable customer term change and resolved effective time. |
| `billing fiscal set` | `ledger-fiscal-calendar/1` | `(installation-admin, change_id)` | Immutable organization fiscal-calendar revision. |
| `billing cumulative setup` | `ledger-billing-cumulative-agreement/1` | `(customer-admin, customer, source, change_id)` | Immutable cumulative basis tied to one exact M2 agreement version. |
| `billing activity` | `ledger-billing-activity/1` | `(customer, source, id)` plus semantic `operation_id` | Immutable additive integer activity quantity. |
| `billing correct` (M5 quantity-correction family) | `ledger-billing-quantity-correction/1` | `(customer, source, id)` | Immutable signed quantity delta; before close it links to its original period, after close it creates a linked adjustment. Existing M4 outcome correction/2 remains unchanged. |
| `billing period resolve` (coordinator-internal) | `ledger-billing-period-resolve/1` | `(customer-admin, customer, logical_period_id)` | Durable later-period boundary resolution. Idempotently materialized before a dependent command when absent; a separate complete snapshot boundary is committed. |
| `billing close` | `ledger-billing-period-close/1` | `(customer-admin, customer, logical_period_id)` | Immutable closed standard statement/4 and presentation claims for included adjustments. The logical period itself is the stable retry identity; no separate caller ID can create a second close. |
| `billing adjustment statement` | `ledger-billing-ad-hoc-statement/1` | `(customer-admin, customer, command_id)` | Immutable ad hoc receivable/payable statement for explicitly named adjustments. |
| `billing recurrence set` | `ledger-billing-recurrence/1` | `(customer-admin, customer, source, change_id)` | Immutable recurrence-rule version tied to an exact M2 agreement version. |
| `billing recurrence cancel` | `ledger-billing-recurrence-cancel/1` | `(customer-admin, customer, source, change_id)` | Immutable cancellation at first successful ledger acceptance time. |
| `billing occurrences` | `ledger-billing-occurrence-query/1` | Read-only; no retry identity | Bounded list of deterministic due occurrence IDs; no charge or mutation. |
| `billing occurrence accept` | `ledger-billing-occurrence-acceptance/1` | `(customer, source, occurrence_id)` plus stable delivery identity | One M3 billable entry accepted under the M2 acceptance-time rule. |
| `billing fiscal report` | `ledger-fiscal-report-request/1` | `(installation-admin, command_id)` | Immutable internal report run pinned to a fiscal-calendar revision and ledger snapshot. |

M5 does not change the input or output meaning of M2/M4 families. A M5 command that receives the wrong customer/source scope refuses before it reads target contents. Organization-level commands have no customer or application source field.

## 2. Effective request fields

### Customer term

`ledger-billing-term/1` contains:

```text
schema, customer, change_id, expected_revision,
effective: { mode: initial | next_boundary | immediate, at?: Timestamp },
term: {
  interval: positive integer,
  unit: day | week | month | year,
  alignment: anchored | calendar_aligned,
  anchor: { date: YYYY-MM-DD, time?: HH:MM:SS[.ffffff] },
  timezone: IANA name,
  week_start?: monday | tuesday | wednesday | thursday | friday | saturday | sunday,
  month_end_rule: preserve_anchor_and_clamp | explicit_end_of_month,
  boundary_rule_version: string,
  timezone_rules_version: string,
  proration: none
}
```

`anchored` derives each boundary by adding the selected interval to the immutable local anchor; monthly/yearly arithmetic is calculated from that anchor, never by repeated advancement. With `preserve_anchor_and_clamp`, use the anchor day-of-month and clamp to the target month's last day; with `explicit_end_of_month`, require the anchor itself to be month-end and use the last calendar day of every target month. This also defines leap-year behavior: an anchored February 29 yearly term clamps to February 28 in nonleap years and returns to February 29 in the next leap year. `calendar_aligned` uses the first natural local boundary on or after the anchor (midnight for days, `week_start` for weeks, day one for months, and January 1 for years), then advances by the selected interval. The anchor remains immutable and determines the phase of multi-unit calendar-aligned terms. A weekly term always requires an explicit `week_start`; a calendar-aligned week boundary is the first chosen weekday at local midnight on or after the anchor. A boundary is resolved with the pinned timezone database: a nonexistent local time moves to the first valid instant after the gap, while an ambiguous time selects the earlier UTC instant. Boundaries form half-open UTC intervals `[start,end)`.

Each immutable term version's logical period index starts at zero; negative indexes are invalid. Period zero starts at the version's `effective_at` and ends at the first scheduled boundary strictly after that instant, using the anchored or calendar-aligned sequence above. Later period indexes advance from that end by the declared interval. This makes the initial active interval explicit even when activation falls between natural calendar boundaries; `proration:none` means no amount is scaled by that short interval. An immediate transition starts the successor version's period zero at the sampled transition acceptance instant. All M4 acceptance timestamps at or after the initial effective instant therefore resolve to exactly one nonnegative period.

Every accepted term-version command appends both the immutable term-version child and its persisted period-zero boundary-resolution child, each with its own M5 record sequence. An immediate transition also appends a successor resolution for the predecessor's still-open logical period, with `supersedes_resolution_id` pointing to the prior resolution; the same command contains the successor term's period-zero resolution. Later periods use the coordinator-internal `ledger-billing-period-resolve/1` command when first needed. Its strict request is `{schema,customer,period_id}`; its family-scoped identity is `(customer-admin,customer,logical_period_id)`, with the same canonical `term_version:period_index` key used by close but a distinct family. It creates one immutable boundary-resolution child and one complete post-command snapshot boundary in one transaction. The operation is accepted only when the period has started, refuses unknown term/period IDs, and never writes an amount or assignment. The coordinator commits it before the first dependent operation that requires a persisted boundary, including a close of an empty period. A close then selects the newest complete snapshot after resolution and before the close command. If interrupted between the two commits, retry safely reuses the saved resolution and continues; it never fabricates a cut inside a command. A close references one retained resolution ID and its backing record sequence at the selected pre-close snapshot.

Initial activation requires explicit `effective.mode=initial` and caller-supplied `effective.at`. If the customer has retained billable M4 history, that instant cannot be later than the oldest retained billable acceptance. For later changes, `next_boundary` resolves to the next boundary of the current term. `immediate` has no caller timestamp: after the writer lock is held, the ledger samples the first successful acceptance instant and uses it as the transition instant. A retry returns the saved response and never resamples. This makes delayed lock acquisition visible in the selected time and prevents caller-selected past/future effective times. The result returns the resolved UTC instant and logical period IDs. An immediate change never edits an existing term or event assignment. If it falls between scheduled boundaries, it creates a short logical period only where the linked agreement explicitly selects `proration:none`; the engine does not synthesize a time-proportional amount.

### Organization fiscal calendar

`ledger-fiscal-calendar/1` contains `schema`, `change_id`, `expected_revision`, organization `timezone`, `calendar`, `timezone_rules_version`, and optional `reason`. `calendar` is a tagged union:

- `gregorian_months`: fiscal-year start month/day and optional week-start day;
- `gregorian_quarters`: fiscal-year start month/day and optional week-start day;
- `gregorian_years`: fiscal-year start month/day;
- `week_pattern`: a fiscal-year end month/day, one of 4-4-5, 4-5-4, or 5-4-4, week-ending weekday, whether fiscal year end is the nearest or last matching weekday, and the period receiving an extra week when the resolved year has 53 weeks. These fields deterministically produce 52- or 53-week years; the extra week is assigned to the declared period.

The active revision is installation-wide. For `week_pattern`, anchor the fiscal year by the declared month/day; select the nearest or last declared week-ending weekday as the fiscal-year end. The next fiscal year starts the following day. A resulting year has 52 or 53 complete weeks; in a 53-week year append the extra week to the declared period. Changing the active revision never changes customer billing terms or an already issued report.

### Cumulative agreement basis and activity

`ledger-billing-cumulative-agreement/1` contains `schema`, `customer`, `source`, `change_id`, `expected_revision`, `agreement_id`, `agreement_version`, `effective_at`, and `basis`:

```text
basis: {
  mode: cumulative_period,
  source_unit: nonempty bounded string,
  billable_unit: nonempty bounded string,
  conversion_numerator: positive integer string,
  conversion_denominator: positive integer string,
  rate_usd_per_billable_unit: exact decimal string with at most 18 fractional digits,
  maximum_period_quantity: positive integer string
}
```

Parse the decimal rate exactly as scale-18 integer atoms per billable unit. The conversion fraction means billable units per source unit, so `E(q) = q × conversion_numerator × rate_atoms / conversion_denominator`, an exact rational scale-18 USD-atom amount. Normalize every exact rational to lowest terms with a positive denominator; represent zero only as `0/1`. Reduce the positive conversion numerator/denominator before acceptance and reject a nonpositive rate or out-of-bound result. The basis names one exact M2 agreement version and its effective interval; no acceptance can select it before that M2 version is active. A new M2 agreement version needs a separately accepted cumulative basis version if cumulative billing continues.

`ledger-billing-activity/1` contains `schema`, `customer`, `source`, `id`, `operation_id`, `target`, `quantity`, `occurred_at`, and `evidence`. Quantity is a positive integer in the basis's source unit. It is additive; replacement totals are not accepted. Delivery identities use `(customer,source,id)`; semantic identities use `(customer,source,operation_id)`. Normalize the complete request with the repository canonical JSON encoder before retaining or comparing delivery ingress. Its semantic-facts bytes are canonical JSON for `{schema:"ledger-billing-activity-facts/1",customer,target,quantity,occurred_at,evidence}`; `id` and `operation_id` are excluded, matching M3's exact completion-facts rule. The first acceptance pins its M2 agreement, M5 basis, billing period, and response. An exact delivery retry returns those saved response bytes. A fresh delivery ID with the same semantic key and exact facts inserts one durable delivery alias to the original activity and returns the original saved response bytes; it appends no command, domain record, quantity, or economic value. Reuse of a delivery ID with changed normalized ingress returns `IDENTITY_CONFLICT`; reuse of an operation ID with changed facts returns `SEMANTIC_CONFLICT`. A delivery alias is permanent and exact retries of it return the same original response. The accepted M2 agreement version and M5 basis version are retained with the activity. Aggregate quantity cannot exceed `maximum_period_quantity` after accepted corrections.

### Quantity correction and outcome correction

`ledger-billing-quantity-correction/1` contains `schema`, `customer`, `source`, `id`, `target`, `quantity_delta`, `occurred_at`, and `evidence`. `quantity_delta` is a signed integer string other than zero. It cannot contain a replacement quantity, rate, unit, agreement ID, or period ID; those are resolved from the retained target. The service checks existing correction authority, agreement-specific permission, evidence, target ownership, bounds, and whether the original logical period is durably closed under the writer lock. The accepted M5 correction record records the resolved `mode`, `unit`, and either the original M2 `agreement_version` or cumulative `basis_version`. A per-work correction to an open period carries its exact `quantity_correction` calculation and owns the signed amount. A per-work correction to a closed period is a nonmonetary support record; a separate adjustment child is the sole monetary owner. Cumulative corrections are nonmonetary support records in either route; before close, the close converts the resulting bucket once, while after close an adjustment child books the cumulative delta.

For a per-work open-period correction, `exact_atoms_numerator = quantity_delta × original_rate_atoms_per_unit`, denominator is `1`, and no additional rounding occurs. The adjustment child after close uses the same original agreement version and rate. For cumulative basis version `v`, define `E_v(q) = q × conversion_numerator × rate_atoms_per_billable_unit / conversion_denominator` and `B_v(q) = nearest_ties_away(E_v(q))`. A close books `B_v(q)` once, including `q=0`. A post-close adjustment carries both nonnegative quantities, both exact rationals, both independently rounded booked totals, the pinned basis version, and `signed_delta_atoms = B_v(q_new)-B_v(q_old)`; this delta has denominator `1` and `rounding:"none"`. The arithmetic equality among these operands is a service invariant and is repeated in the exact oracle, not delegated to JSON Schema.

M4 `ledger-billing-correction/2` remains the authoritative accepted outcome-correction command with its existing `id`, `target`, `expected_revision`, and `replacement` fields. Its exact M3 append and unique M5 allocation projection commit atomically under the existing `(customer, source, id)` delivery identity. Preserve its existing response bytes and receipt; the M5 projection is not a second monetary posting. For customer statements, allocate the correction to the logical period previously assigned to the outcome being corrected while that outcome period remains open; otherwise allocate its signed target-net difference to the period containing correction acceptance. Do not use the M4 work target's earlier period when the corrected outcome was first accepted later. For internal fiscal reporting, include only the signed M3 posting at its own acceptance time. A first outcome supplied after the work-target period ends is a new fact and always uses its own acceptance-time period. Fiscal inclusion has one monetary owner: the M3 posting; the M5 assignment/adjustment projection is reference-only. The calculation union explicitly distinguishes a first outcome, replacement, and reversal; a reversal retains the prior outcome reference and represents the accepted replacement amount as zero.

### Close and ad hoc presentation

`ledger-billing-period-resolve/1` contains exactly `schema`, `customer`, and `period_id: { term_version, period_index }`. It is coordinator-internal and is invoked only when the requested later period has no retained resolution. Its accepted command stores the deterministic boundary-resolution child, exact response bytes, and post-command complete snapshot atomically. The period-resolve command key is the customer plus logical period ID; retries return the original resolution response even if a later transition appends a superseding resolution. A period already resolved by term setup or a transition is reused directly and does not create another materialization.

`ledger-billing-period-close/1` contains `schema`, `customer`, and `period_id: { term_version, period_index }`. The customer and logical-period pair is the unique close identity. The request does not supply calculated totals, boundary values, or source record lists. Before selecting its close snapshot, the coordinator commits the period-resolve command if this period has never been materialized. The close then pins the newest complete pre-close snapshot containing the resolution, exact boundaries, accepted high-water marks, sorted included source IDs, line calculations, exact totals, statement/4 bytes, and hash. Resolving a period and closing it are separate atomic commands and snapshot boundaries; the close snapshot never ends inside either command. Retrying a close after a crash between resolution and close resumes from the saved resolution; retrying a committed close returns its exact result before current revision checks. A second statement for that logical period is impossible.

`ledger-billing-ad-hoc-statement/1` contains `schema`, `customer`, `command_id`, and a sorted, duplicate-free nonempty `adjustments` array of `{source, adjustment_id}` references sorted by `(source, adjustment_id)`. The source is required because application identities and adjustment IDs are customer/source scoped. It can include post-close adjustments only. The command issues the statement atomically and creates a unique presentation claim for each included adjustment. Preparing a request or choosing the ad hoc option does not claim anything. Standard close includes every otherwise eligible adjustment lacking an ad hoc presentation claim, and claims it in the close transaction. Close and ad hoc issue serialize; only the first committed presentation succeeds.

The standard statement is `ledger-billing-statement/4`. It presents only that logical period's exact net, does not carry earlier balances, contains customer-scoped receipt/adjustment references and per-line calculation provenance, and reports `direction` as `receivable`, `payable`, or `none`. A negative net is payable. Sort all source references by `(customer, source, kind, id)`; this tuple is the complete source identity, including inside one customer's statement. Sort statement lines by `line_id`; each line ID is lowercase SHA-256 of `bean-counter/m5/statement-line/1\0` followed by canonical JSON `{view_kind,view_identity,line}` where `line` is the complete line object with `line_id` omitted and its `source_records` sorted by the tuple above. The literal `view_kind` is `standard` for a standard statement, `ad_hoc` for an ad hoc statement, and `fiscal` for a fiscal report. `view_identity` is `{customer,period_id}` for a standard statement, `{customer,statement_id}` for an ad hoc statement, and `{calendar_version,start_utc,end_utc,m3_high_water,m5_high_water}` for a fiscal report. Each line carries one agreement/version and its accepted payer/recipient roles. Its exact numerator, positive denominator, booked atoms, rounding mode, and typed formula operands must reconcile to `amount_atoms`; cumulative close lines retain the exact rational and identify the one `nearest_ties_away` rounding, while post-close cumulative deltas identify `B(q_new)-B(q_old)` with no second rounding. The statement hash is lowercase SHA-256 of `bean-counter/m5/statement/4\0` plus canonical JSON of the complete result with `statement_hash` omitted. The ad hoc hash uses `bean-counter/m5/ad-hoc-statement/1\0`; fiscal report hash uses `bean-counter/m5/fiscal-report/1\0`. The ad hoc statement is `ledger-billing-ad-hoc-statement-result/1`; it includes only explicitly named customer/source-scoped adjustments, has the same direction rule, and is not a tax/legal invoice. Neither family asserts collection or settlement. Finance CSV export is `ledger-finance-export/4`, carries exact scale-18 integer atoms as text, and contains a completion row; it does not imply delivery or payment.

### Recurrence and fiscal report

`ledger-billing-recurrence/1` contains `schema`, `customer`, `source`, `change_id`, `expected_revision`, exact `agreement_id`/`agreement_version`, and an immutable rule with interval, unit, local anchor, IANA timezone, `effective_from`, boundary-rule version, pinned timezone-rules version, and `proration:none`. Its end is derived from the exact linked M2 agreement version's effective end; the caller cannot extend recurrence beyond that agreement. Recurrence versions are monotonically allocated and unique within `(customer,source)`, even when an agreement version changes; query and cancellation therefore resolve the same stable version key. The stable occurrence ID is `occ_` followed by lowercase hex SHA-256 over `bean-counter/m5/occurrence/1\0` and canonical JSON `{customer,source,agreement_id,agreement_version,recurrence_version,scheduled_local_label}`. The scheduled local label is `YYYY-MM-DDTHH:MM:SS[.ffffff]` without an offset; the pinned timezone-rules version resolves it to one UTC instant using the same gap/overlap rules as billing periods. Occurrences are due when the resolved instant is no later than `due_through` and the request is processed at/after that instant. The query request gives an explicit `due_through`, bounded `limit`, and optional opaque page cursor; it is read-only. The result returns `has_more` and, when true, a cursor for the next page so a bounded response cannot silently omit due occurrences.

Occurrence acceptance is an operator-triggered M3 bridge for one successful `content.generated` work event. The nested event uses the existing M4 `ledger-event/1` shape and must have `customer` equal to the request customer, `id` equal to the deterministic `occ_` occurrence ID, and `status:"succeeded"`. For fixed-price M2 terms, `quantity` and `unit` are omitted; for usage terms, both are required and quantity must be a positive integer in the agreement's unit and bounds. The event is accepted through the unchanged M4 evaluator. The returned `receipt` is the exact existing `base-acceptance` canonical record envelope, including its embedded `body.original_receipt_utf8`; the M5 occurrence-acceptance child links the envelope's `id`, scheduled label, assigned billing period, and M5 command. An exact retry of an occurrence already accepted through M5 is resolved from the retained M5 identity before calling M4 and returns the original successful M5 result bytes, including after recurrence cancellation. Existing direct M4 acceptance keeps its `duplicate` status and kind. If no M5 occurrence link exists but M4 already retains the external occurrence ID or the event's semantic `operation_id`, M5 refuses with `BILLING_M5_OCCURRENCE_CONFLICT`; it does not attach another route's receipt or append a partial link. This includes a semantic hit for a different external event ID. Its acceptance time—not scheduled time—selects the M2 agreement version, customer billing period, and fiscal period. It cannot create a cumulative-activity charge; those quantities remain nonmonetary until a period close. Failed work, any other event type, a quantity/unit mismatch, or acceptance after the linked M2 agreement end is refused without a partial M3/M5 commit.

`renewal` is a tagged object. `{"mode":"manual"}` creates no renewal authorization. `automatic_opt_in` requires a preaccepted immutable M2 amendment for the same customer/source, a named successor agreement version, and an explicit successor recurrence rule. The referenced M2 amendment must already exist, be the immediately following agreement version, and carry the exact renewal setup/pricing/evidence/permissions; the successor rule must pin its own interval, anchor, timezone, boundary and timezone-rules versions, and `proration:none`. In the same atomic recurrence command, M5 stores both the current recurrence version and its preauthorized successor as separate immutable children; the successor consumes the next source-wide recurrence version and remains inactive until its exact M2 effective time. The successor configuration may be accepted before that date; successor occurrences cannot be accepted before it. This materializes terms only. Automatic renewal never invents or copies price terms, charges an occurrence, runs a background job, or catches up missed occurrences. Each occurrence still requires an operator-triggered acceptance, and a later automatic renewal requires another explicit M2 amendment and recurrence version.

`ledger-billing-recurrence-cancel/1` is a separate customer/source-scoped operator control with `change_id`, expected recurrence revision, and recurrence version; it carries no `effective_at`. Its successful acceptance instant, sampled after the writer lock, is the cancellation instant. It appends one immutable cancellation record and prevents acceptance of not-yet-accepted occurrences at or after that instant. An accepted M5 occurrence retried after cancellation returns its original successful M5 result bytes and original `base-acceptance` receipt-envelope bytes; direct M4 submissions retain M4's own duplicate response. This cancels that recurrence only; ending all agreement-backed work remains the existing M2 agreement-ending command, whose future-effective behavior and wire contract are unchanged. Cancellation, successor M2 amendment, and recurrence setup serialize with occurrence acceptance.

`ledger-fiscal-report-request/1` contains `schema`, `command_id`, an exact `calendar_version`, a half-open fiscal interval, and optional retained snapshot high-water marks for an explicit historical rerun. Start and end must be resolved boundaries of the selected calendar version. Without an explicit snapshot, the selected version must still be active at commit or the request fails stale; with an explicit snapshot, the exact `(m3_high_water,m5_high_water)` pair must exist in immutable `billing_m5_snapshot_boundaries`. Every versioned recurrence uses a monotonically increasing source-level version, so its cancellation/query key `(customer,source,recurrence_version)` is globally unique across M2 agreement versions. Each accepted occurrence still pins its exact agreement and recurrence versions. The boundary row is appended in the same writer transaction as every schema-11 M3 or M5 mutation, after all of that mutation's M3 and M5 children. A newly retained M5 activity delivery alias is also a mutation: it appends a boundary with unchanged M3/M5 high-water marks, while an exact alias retry changes no state. Distinct mutations may retain the same high-water pair when an M3 semantic alias or M5 activity delivery alias changes retry metadata without adding an economic ordinal or M5 record; those rows have distinct boundary IDs and equality does not violate monotonicity. An exact retry of a retained alias changes no state. An explicit high-water pair resolves to its greatest retained boundary ID; nonexistent, future, and torn pairs refuse. A normal run pins the latest complete pair before appending its report command/record; the report is excluded from its own snapshot, while the post-report state gets its own boundary. Output `ledger-fiscal-report/1` pins the exact calendar/timezone versions, boundaries, snapshot, sorted customer-scoped included IDs, exact monetary effects, separate nonmonetary quantities, totals, and content hash. Monetary inclusion follows the event table in the architecture; report runs and statement presentation claims never add economic value themselves.

Assignments and adjustment links are projection rows and never consume `billing_m5_records.sequence`. Their `source_stream` and `source_sequence` point to the authoritative M3 or M5 record. Snapshot high-water marks therefore track the two authoritative record streams only. The same pair may identify more than one immutable boundary row; pair-only historical requests resolve to the greatest matching `boundary_id`. The Unicode canonicalization vector in [m5-oracle.json](../contracts/candidates/billing-lifecycle-m5/vectors/m5-oracle.json) distinguishes the repository's UTF-16 object-key order from UTF-8 byte order.

## 3. Identity, ordering, errors, and retries

Identity is command-scoped and family-specific. For each accepted M5 write, `billing_m5_commands` stores one stable identity key, one request, and one response; `billing_m5_records` stores one-or-more domain children linked by `command_sequence`. Child rows never claim command identity. The unique key bytes are UTF-8 canonical JSON for `{schema:"ledger-billing-m5-command-identity/1",domain,family,key_kind,key,customer?,source?}`, with organization scope fields absent (not null) and required fields included, encoded with the repository `CanonicalBytes` rules: object keys sort by UTF-16 code-unit order, strings use the existing `serde_json` UTF-8 escaping, arrays retain order, there is no whitespace, numeric tokens are safe integers only, and duplicate keys are rejected before conversion. This exact object is the unique key BLOB. A command and all linked domain children commit atomically; replay returns the saved response and complete linked child set. Assignment and adjustment-link rows are normalized projections over M3/M5 sources, not domain children; they are inserted or rebuilt atomically with their source change, including initial history backfill, and do not consume the M5 command/record cap. A post-close M4 outcome correction remains one authoritative M3 posting; M5 stores only its linked adjustment projection, never a duplicate monetary domain record. Missing children or a child whose hash/link fails reconciliation is `BILLING_M5_INTEGRITY`.

Cumulative activity identity retention is separate from M3 aliases. The first accepted activity atomically inserts one row in `billing_m5_activity_semantics` and one in `billing_m5_activity_deliveries`, both linked by `(command_sequence,activity_sequence)` to its original command and activity record. Semantic rows are unique on `(customer,source,operation_id)` and retain the exact canonical fact bytes; delivery rows are unique on `(customer,source,external_id)` and retain the normalized full request bytes. The delivery checksum is SHA-256 of `bean-counter/m5/activity-ingress/1\0` plus ingress bytes; the semantic checksum is SHA-256 of `bean-counter/m5/activity-facts/1\0` plus facts bytes. Both rows are immutable. Resolve a retained delivery key first, then a semantic key, before checking current term, basis, or permission revisions. A semantic alias inserts one additional delivery row referencing the original command/activity, without an M5 command or domain child; this mutation appends a snapshot boundary with unchanged high-water marks. The original delivery row equals the saved canonical command request; every alias row recomputes to the linked semantic-facts bytes, and all rows resolve to the original response and activity record. Store open and every identity lookup verify these relationships. A changed same-delivery request returns `IDENTITY_CONFLICT`; changed facts under a retained semantic key return `SEMANTIC_CONFLICT`. Activity index rows and their exact bytes count toward M5 retention limits.

Every domain-separated hash concatenates the literal UTF-8 domain prefix, exactly one raw zero byte (`0x00`), and the specified payload bytes. A notation such as `\0` means that one byte; the two printable characters backslash and `0` are never hashed in its place. The golden uses U+10000 and U+E000 property names because UTF-16 order places U+10000 first while UTF-8 byte order places U+E000 first.

Existing M2/M3/M4 delivery and control identities retain their established ingress normalization, canonical facts, customer/source scoping, and exact response behavior; M5 does not redefine how whitespace/key ordering or semantically identical deliveries are compared there. New M5-only controls use the family keys in the request table and require byte-identical retries; a changed request under the same retained identity returns `IDENTITY_CONFLICT`. The exact `key_kind`/key pair is `change_id` for term, fiscal-calendar, cumulative-basis, recurrence, and cancellation controls; `delivery_id`/request `id` for activity and quantity correction; `occurrence_id` for occurrence acceptance; `command_id` for ad hoc statements and fiscal reports; and `logical_period_id` for period close. M5 cumulative activity uses the explicit exact-facts encoding and durable alias tables above; recurrence acceptance delegates its semantic comparison to the unchanged M3 evaluator. Organization controls have the `installation-admin` domain and no customer/source; customer/source recurrence controls include both fields. A close uses `(customer-admin, customer, "logical_period_id", key)`, where `key` is the two canonical nonnegative decimal strings `term_version` and `period_index` joined by one colon (for example, `1:12`). Since neither component contains a colon, this encoding is unambiguous and stable.

Resolve a retained identity before current agreement, calendar, term, or permission revision checks, while still enforcing the existing M2 authority required to read/resolve it. Acquire the SQLite writer transaction before reading mutable authorization, target quantities, target outcome revisions, open/closed state, presentation claims, or next revision. Generate the accepted timestamp only after the writer lock is held. Commit the M5 command, every domain child, M3 cross-link (when applicable), period/allocation indexes, bounds counters, snapshot-boundary pair, and exact response bytes atomically. A transaction that mutates M3 but produces no M5 domain child still appends a snapshot-boundary pair atomically with the M3 commit.

The M5 command responses remain command-specific, as in the existing billing CLI. The result schema is additive; where an operation returns an existing M3 receipt, its exact existing receipt object is retained:

## 4. Persistence and upgrade contract

New installations start at ordinary SQLite writer schema 11. Schema-10 installations require explicit `billing upgrade --json`; normal open and every ordinary write refuse before mutation while schema 10 is present. Preflight validates all existing installation/configuration data and verifies each `billing_m3_index` row against exactly one retained decision bundle in its original tier: `billing_entries` (legacy scope derived by the existing legacy setup rules), `billing_m2_entries`, or `billing_m3_entries`. Existing tier integrity rules prove its customer/source, receipt, accepted timestamp when recorded in that tier/index, agreement version where present, amount, and derived M3 index fields. Duplicate/missing tier matches, invalid legacy derivation, or any mismatch refuses. Migration creates only additive M5 sidecar tables/indexes, preserves all M1–M4 table names, bytes, rows, aliases, identities, agreements, outcomes, and statement projections, and advances `PRAGMA user_version` to 11 in one transaction under the existing exclusive owner lock. Any mismatch refuses before schema change. An unknown result is reconciled by reopening: schema 11 plus exact M5 migration identity means complete; schema 10 permits retry of the same explicit upgrade; any partial/unrecognized state fails closed.

Schema-10 writers refuse schema 11 before mutation. Schema-11 support is source-build-qualified separately; it does not establish native artifact, other host, or general volume conformance. No ordinary open implicitly upgrades a database. M5 does not modify `contracts/schemas/v1/canonical-records.schema.json`, its frozen fixtures, `contracts/freeze.json`, or the frozen first-slice family.

The sidecar stores one immutable command row per accepted write (identity key, exact request bytes, exact canonical response bytes, accepted time, and domain-separated request/response hashes) and one-or-more immutable domain child rows (stable record ID, command sequence, canonical payload bytes, and domain-separated payload hash). Each child key is canonical JSON `{role,customer?,source?,kind,key}`; omitted scopes stay absent, `kind` is the child record family, and `key` is the family's stable natural key encoded as a JSON value. Child IDs are `m5r_` followed by lowercase hex SHA-256 over `bean-counter/m5/record-id/1\\0`, the command identity-key bytes, a NUL byte, and the child-key canonical JSON bytes. Child keys are unique within one command and determine child insertion order by their canonical JSON bytes. The request hash is SHA-256 over `bean-counter/m5/request/1\\0` plus exact request bytes; the response hash is SHA-256 over `bean-counter/m5/response/1\\0` plus exact response bytes; the payload hash is SHA-256 over `bean-counter/m5/record/1\\0`, family UTF-8, NUL, and the canonical domain payload with only `record.payload_hash` omitted. The other record-envelope values (`record_id`, `sequence`, `accepted_at`, and `command_sequence`) remain in the payload-hash input. Request and response storage metadata is outside their respective hash inputs, and the response does not embed its own `response_hash`; that hash is stored only in `billing_m5_commands`. `canonical_json` uses the repository `CanonicalBytes` encoder: UTF-16 code-unit object-key ordering, the existing `serde_json` UTF-8 string encoding, preserved array order, no whitespace, safe integer tokens only, and duplicate-key rejection before conversion. M5 request schemas do not accept null; the encoder limits nesting to 32 levels. Hash-domain components end with one zero byte (`00` in hexadecimal), never the two printable characters backslash and zero; component text and family names are UTF-8 bytes. A derived period/allocation/presentation index is checked against its M3/M5 source records during store open and before high-risk writes. Mirror the existing M3 fail-closed pattern: cap M5 commands, domain records, and retained activity-identity rows at 100,000 total rows and 268,435,456 combined exact request, response, payload, identity-key, activity-ingress, and semantic-facts bytes, with no pruning or automatic expiry. `billing_m5_state.activity_identity_count` and `activity_identity_bytes` are monotone counters reconciled against both activity identity tables at open; any limit failure returns `BILLING_M5_BOUNDS` before mutation. Assignment projections and snapshot-boundary metadata are separately bounded by the M3/M5 source-row ceilings. A limit failure returns `BILLING_M5_BOUNDS` without changing any sidecar/M3 row or counter.

The M5 cap is 100,000 combined command, domain-record, and activity-identity rows plus 268,435,456 bytes across exact request, response, payload, command identity-key, activity-ingress, and semantic-facts data. Assignment and adjustment-link projections and snapshot-boundary metadata are bounded separately by retained source mutations. A post-close M4 outcome correction remains an M3 posting with an M5 adjustment-link projection; the projection links to exactly one source stream and ordinal and is never charged again as an M5 domain record.

## 5. Frozen contract vector coverage

The frozen Package 3 synthetic oracle includes deterministic inputs and exact expected assignment/arithmetic/identity outcomes for these cases. Every mutating command scenario has its complete request, identity key, response, domain children, stream cuts, canonical bytes, and golden hashes in [`m5-command-goldens.json`](../contracts/candidates/billing-lifecycle-m5/vectors/m5-command-goldens.json). Read-only calculations and refusal cases carry exact source state and request, exact output/error, and an explicit no-mutation assertion; they do not invent persisted record hashes when no record is written.

1. Jan 1–Feb 1 logical period, no close until Feb 5: a Feb 2 signed correction commits first and appears in that January statement; it retains Feb 2 as its fiscal timestamp. If close commits first, the same economic change is a post-close adjustment in the period containing its acceptance time.
2. A first outcome accepted after Jan 31 period end belongs to its later acceptance-time period even if January's statement is not yet closed. A subsequent correction to that outcome links to the first outcome's assigned logical period only while that target period remains unclosed; otherwise its signed difference is allocated to the correction-time period.
3. A Jan 15 immediate schedule transition appends a successor boundary resolution for the still-open January logical period, preserving `(customer, old_term_version, period_index)` assignments. Close retry after a newer term becomes active returns the first saved statement without consulting the newer boundary head.
4. For exact cumulative `E(1)=0.5` atom and `E(2)=1.0` atom, both `B(1)` and `B(2)` are 1 atom; a post-close quantity increment from 1 to 2 books `B(2)-B(1)=0`, not a separately rounded half atom.
5. A cumulative activity record and its pre-close correction are nonmonetary in the fiscal report; the period close contributes `B(q)` once. A post-close cumulative correction contributes `B(q_new)-B(q_old)` once. The sequence telescopes exactly.
6. Prepare an ad hoc presentation request without issuing it, then standard close: the standard close includes the adjustment. Issue ad hoc first: standard close excludes it. Race both writes: exactly one claim commits; the other resolves to the committed presentation or refuses.
7. Two customers reuse the same source/control ID without collision; an organization-level fiscal command has no customer; a customer-level term command cannot collide with the organization identity domain.
8. Fiscal report replay with the same calendar revision and complete M3/M5 boundary pair returns byte-identical report content; a nonexistent/torn pair refuses and a retained pair replays exactly.
9. Boundary arithmetic for day/week/month/year, leap day, explicit month end, week-start alignment, fiscal 52/53-week years, and the exact pinned tzdb release.
10. Usage quantity deltas at zero and configured maximum bounds, an unauthorized correction, a close/correction writer-lock race, and a changed-identity/changed-semantic retry conflict.
11. Recurrence cancellation at the sampled acceptance instant; retry of a previously accepted occurrence after cancellation; explicit automatic-renewal successor M2 amendment and recurrence; missed occurrence remains uncharged; fixed and usage-mode event payloads; exact M4 `base-acceptance` receipt-envelope provenance; and refusal when M4 already retains the delivery or semantic identity without an M5 occurrence link. The recurrence command golden includes request/response/payload bytes and both M3/M5 high-water cuts.
12. A fiscal report with two customers reusing the same source and event ID retains both rows and amounts because references are keyed by `(customer,source,kind,id)`.
13. Mixed schema-10 history with legacy, M2, and M3 retained tiers upgrades; missing, duplicate, hash-mismatched, unknown-commit/reopen, and already-upgraded states have exact outcomes and preserve source bytes.
14. Delayed writer-lock acquisition selects the post-lock timestamp for an immediate term change; exact retry after the lock/time advances returns the first response bytes.
15. An empty later period is materialized with `ledger-billing-period-resolve/1` in a separate atomic transaction; the close pins the resulting complete pre-close snapshot, and close retry returns the exact saved empty statement bytes without another record.

These vectors are contract examples, not implementation or conformance evidence. Package 3 closed after each case had machine-readable expected inputs/outputs, schemas for all listed request/result/domain-command families, complete command goldens for accepted writes, exact no-mutation outcomes for refusals and queries, a reviewed migration DDL/preflight contract, and independent Sol and Astra reviews. Implementation and qualification are now authorized as separate gates.
