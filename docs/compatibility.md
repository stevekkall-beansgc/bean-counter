# Compatibility policy

The contract family is `ledgerlab-contracts/1`. The current published native release is [v0.3.0](https://github.com/stevekkall-beansgc/bean-counter/releases/tag/v0.3.0); the Rust workspace packages are version `0.3.0` and are not published to crates.io. The local billing facade contract is `v0.2`. The development toolchain is pinned to the verified Rust 1.98.1 release; this is not an MSRV claim. See the [current public status](../STATUS.md) for supported platforms and deferred capabilities.

Event/link/terms schema, DSL, evaluator semantics, canonical/hash profile, HTTP, logical storage/backend migration and export versions evolve independently. Preserve old canonical bytes and IDs. A changed numeric/order interpretation needs a new evaluator semantics version even if its JSON shape is unchanged. Unknown economic discriminators fail closed. Import must reject unsupported requirements before loading; startup must reject unsupported write schemas. No automatic downgrade or historical rerating.

The first public v0 retains evaluator1 for original replay. Reading booked history never requires rerunning an evaluator. Correcting historic errors requires authorized compensating events. Coordinated 0.x minor releases may document breaking CLI/SDK changes; patches preserve contracts except explicit correctness/security fixes. Public releases require the Bean release gates and exact-artifact evidence; the v0.3.0 release provides that evidence for the bounded local SQLite profile, not deferred full-platform support.

## Local billing CLI/JSON and storage policy

The ordinary local billing CLI consists of separate request, installation, receipt, statement, export, response, and error families. A version marker on one family does not version another. Some successful responses do not emit a family marker, and there is no universal CLI success envelope. The [billing CLI contract](billing-cli-contract.md) describes the observed behavior for a named source/build and profile; integrations must identify the binary they run rather than treating an absent marker as version negotiation.

Within a documented support range, preserve each command family's documented inputs, JSON status and field types, exit-code meanings, monetary interpretation, identity/retry behavior, and unknown-result semantics. Add response fields only when that specific response contract allows them; otherwise treat a shape change as breaking. Do not silently wrap existing successful responses in a universal envelope. Under the existing 0.x rule, a coordinated minor release may make a documented breaking CLI/SDK change; a patch preserves the contract except for explicit correctness or security fixes. Release notes must identify any breaking family and the migration boundary. This is not a promise that every earlier 0.x binary remains supported indefinitely.

Each release must state the exact prior CLI/JSON and storage versions it supports, backed by evidence for the named source/build and platform profile. A missing support range is not an implicit compatibility promise. A breaking family change must name the affected family and its new version or documented 0.x release boundary; it must not silently change behavior under an unchanged contract.

The demonstrated ordinary billing store is local SQLite schema 8. Source-built v0.3.0 and v0.4.0 reopened the same schema without a production migration; v0.4.1 changed documentation and caller examples only. This evidence does not qualify a new store format, a published native artifact, a cross-host profile, or every historical store. The current writer checks its supported SQLite version and migration history before accepting writes and refuses an unsupported newer schema. Do not infer that every future binary will open, upgrade, or downgrade every earlier store.

Before a future production format accepts writes, its release must name the supported source versions and exact transition, reject unsupported stores before mutation, and qualify either an in-place migration or a verified fresh-store transfer. Qualification must reconcile retained accepted records and identities, setup/authority and permission state, receipts, aliases, reports and totals, plus the backup cutoff and recovery procedure. A new or empty store must never silently replace an existing installation. The transition must be tested on the exact source versions before the new format is enabled. This is an activation gate for an actual format change; it does not claim that a future format or refusal case has already been tested.
