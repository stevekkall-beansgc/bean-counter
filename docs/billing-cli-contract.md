# Billing CLI integration contract at v0.3.0 and v0.4.0

This page describes behavior visible in the ordinary local SQLite `ledger billing` implementation at these two source tags. v0.3.0 is the current native-package release for ordinary billing. [v0.4.0](https://github.com/stevekkall-beansgc/bean-counter/releases/tag/v0.4.0) is a published source release with no new native binaries; it leaves the v0.3.0 native assets unchanged. Record the exact source commit and binary used by an integration.

## Command and format boundaries

`ledger billing --directory DIR accept REQUEST --json` accepts an existing strict `ledger-event/1` JSON file. The base event supplies stable `id` and `operation_id`; the installation supplies the trusted source, customer, terms and authority. Keep the complete submitted bytes in a caller-owned durable outbox before invoking the CLI. `id` is the delivery identity and `operation_id` is the semantic work identity. Reusing an identity with changed input or economic facts refuses. A newly invented ID is not a recovery method.

The ordinary billing CLI also exposes `init`, `setup`, `outcome`, `correct`, `permissions`, `explain`, `statement` and `export-csv`. The existing input and storage discriminators include `ledger-local-billing/1` for setup, `ledger-billing-installation/1` for `billing.json`, and `ledger-billing-statement/1` for statements and target explanations. The generic CLI uses `ledger-cli/1` on applicable generic errors and commands. **Ordinary billing `accept` success is not wrapped in `ledger-cli/1`:** accepted output is `{status:"accepted",receipt:...}`; duplicate output is `{status:"duplicate",kind:"identity"|"semantic",receipt:...}`. Do not require a nonexistent schema field on those responses. This is an explicit interface gap for clients that want one universal CLI envelope; changing it requires a separate contract decision.

## Version families and command outputs

There is no single version marker for the whole billing CLI. The source declares a billing-facade constant `v0.2`, but it is not emitted in command output. The version markers below belong to separate input, storage, receipt, statement and export formats. Do not use one as a proxy for another.

| Command | Versioned input or stored format | Observed successful JSON |
|---|---|---|
| `billing init DIR --setup FILE` | Setup file uses `ledger-local-billing/1`; created `billing.json` uses `ledger-billing-installation/1`. | `{status:"initialized",directory,profile:"local-retail",dispatch:"disabled"}`. No `schema` field. |
| `billing setup DIR [--setup FILE]` | Same setup format. | Same initialized result plus the validated customer/agreement/price, setup-copy retention fields and source-build version. Guided setup prints the terms summary and supplied attestations to stderr before confirmation. |
| `billing accept FILE` | Request is `ledger-event/1`; retained base receipt is a `base-acceptance` record. Its embedded `original_receipt_utf8` decodes as `ledger-base-receipt/2-candidate.4`. | `{status:"accepted",receipt}` or `{status:"duplicate",kind:"identity"|"semantic",receipt}`. No response `schema` field. |
| `billing outcome FILE` | Request is `ledger-billing-outcome/1`. | `{status:"accepted",receipt}` or duplicate with `kind` and original receipt. No response `schema` field. |
| `billing correct FILE` | Request is `ledger-billing-correction/1`. | `{status:"accepted",receipt}` or duplicate with `kind` and original receipt. No response `schema` field. |
| `billing permissions` | Reads retained permission history; no request marker. | `{status:"ok",revision,permissions,changes}`. No response `schema` field. |
| `billing permissions FILE` | Change request is `ledger-billing-permissions/1` and carries `expected_revision`. | `{status:"permissions_updated",revision,permissions}`. No response `schema` field. |
| `billing explain TARGET` / `billing statement --customer CUSTOMER` | Read projection is `ledger-billing-statement/1`. | `{schema:"ledger-billing-statement/1",status:"ok",...,complete:true,entries:[...]}`. `explain` filters to one target; `statement` covers the installation at its cutoff. |
| `billing export-csv ...` | Mapping input is `ledger-finance-mapping/1`; output file is CSV with a final `complete` row. | `{schema:"ledger-finance-export/1",status:"exported",complete:true,...}`. This acknowledges only the file export, not delivery or payment. |

Billing commands print JSON on success by default (pretty-printed); `--json` selects compact JSON. Ordinary error objects with `status:"error"` render as text on stderr without `--json`; with it, most use `ledger-cli/1`. The two unknown-commit results instead print JSON to stdout even without `--json`: event submissions use `ledger-cli/1`, while permission updates return the special unversioned `{status:"outcome_unknown",code:"BILLING_CONTROL_OUTCOME_UNKNOWN",...}` object. Therefore automation should branch on command-specific statuses and exit codes and must not require a universal envelope. Do not infer that a permission update rolled back from an unknown result; inspect `permissions` before retrying.

Across these command families, the observed error exits are: 2 for usage, config and local file errors; 3 for other request or state rejections; 4 for identity/semantic conflicts; 6 for unauthorized or wrong-scope requests; 7 for busy, unavailable or read-budget-limited operations; 8 for unknown commit outcomes; and 9 for retained-data integrity failures. There is no ordinary billing “waiting” result/exit in these paths. Rejection codes map to exit 4 only for `IDENTITY_CONFLICT` and `SEMANTIC_CONFLICT`, and to exit 6 only for `SOURCE_UNAUTHORIZED`, `BILLING_UNAUTHORIZED` and `BILLING_SCOPE`; other service rejections, including stale permission revisions and not-found targets, use exit 3. After `export-csv` arguments validate and the installation opens, operation failures additionally report `complete:false` and an `export_warning`; usage and installation-open failures do not. A complete destination can exist if the final directory sync failed. See [CSV export behavior](finance-csv.md).

The `billing accept` receipt is a retained `base-acceptance` record with an `id` and `body.target`. An identity retry returns the original receipt. A different delivery `id` with the same `operation_id` and economic facts may be accepted as a semantic duplicate alias; it also returns the original receipt. `explain TARGET` shows the original entry, not a separate alias entry. For an acknowledgment, verify the receipt against `ledger billing --directory DIR explain TARGET --json`: the explanation must be a complete `ledger-billing-statement/1` target history containing a base entry with the same target and exact receipt object/ID, whose retained event record has the submitted `operation_id`. The entry's `external_id` can be the original delivery ID rather than an alias ID. Save that receipt durably in the caller outbox. On subsequent identical retries, compare the returned receipt to the saved one. This comparison detects an unexpected change in the caller's acknowledgment; the ledger's own retained-history checks remain authoritative.

For this command, exit 0 with `accepted` or `duplicate` is success. Exit 2 means usage or local input error; 3 is rejection; 4 is identity or semantic conflict; 6 is unauthorized or wrong scope; 7 is unavailable storage; 8 is an unknown commit result; 9 is retained-data integrity failure. Inspect both exit code and JSON status. On exit 8, leave the exact request pending without an acknowledgment. Reopen the same installation and retry the saved request bytes with the original IDs; an `accepted` or `duplicate` result is acknowledged only after receipt verification. An unknown result does not establish rollback. An unavailable result also leaves the request pending. Permission-control uncertainty has its own reconciliation procedure and is outside this accept example.

The [Python](../examples/integration/billing_outbox.py) and [Node.js](../examples/integration/billing_outbox.mjs) examples implement this narrow caller flow using synthetic inputs. Invoke either as `LEDGER BILLING_DIR EVENT_JSON OUTBOX_DIR`. The installation must already exist; the outbox parent must exist. Use one caller implementation and language per outbox: the two examples serialize pending receipt files differently. The caller requires the outbox directory to have no group or other permission bits, synchronizes its parent on every invocation, durably binds the outbox to the canonical installation path and refuses a later path change. That marker prevents an accidental path switch; it does not detect rollback or replacement of an installation at the same path. Keep and reconcile the outbox and installation as separate records during recovery. The caller synchronizes the saved request before every submission and the verified receipt before acknowledgment, including restart paths. These examples require one caller process per outbox and a private, durable local filesystem whose write, sync, rename and directory sync operations work. The Node example caps captured CLI output at 128 MiB and fails without acknowledgment if that limit is exceeded; this is a caller limit, not a product history limit. These examples do not create terms, authorize work, invoke a provider, or decide outcomes.

## Reopen and future versions

The production SQLite write schema is version 8 in both v0.3.0 and v0.4.0; no production migration was added between them. A quiescent whole-installation copy can be reopened with the matching v0.3.0 or v0.4.0 implementation subject to the documented local storage and platform limits. Preserve `billing.json`, `.ledger/local.db`, `owner.lock` and any present SQLite sidecars. Stop all writers before copying and keep only one copy active. Use a complete statement, permission status and identical receipt retry to check a restored copy. See [billing recovery](billing-recovery.md).

The current writer checks SQLite `PRAGMA user_version` and the migration history/checksums. A v0.3.0 or v0.4.0 binary refuses a future unsupported production write schema instead of silently admitting it. This refusal behavior does not promise that every future binary can read or upgrade every older store. The product's supported-range and future-format policy is stated in [compatibility](compatibility.md). This page remains an observed contract for the named source tags; it does not extend the v0.3.0-to-v0.4.0 result to a future schema or qualify the v0.3.0 native artifacts under v0.4.x.

The opt-in `admission/1-candidate.1` work introduced at v0.4.0 has its own marker, journal and CLI feature. It is synthetic, experimental and separate from ordinary production billing history. Its records are not a billing migration or an import path.
