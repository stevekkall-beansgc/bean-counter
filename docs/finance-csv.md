# Generic finance CSV export

The facade projects verified retained `base-posting` and `action` records from a complete current billing statement. It does not evaluate a new price, edit history, create new obligations, select accounting policy, acknowledge delivery or collect money. This is a generic data export, not a vendor-specific import format or double-entry journal.

## Command and mapping

`ledger billing --directory DIR export-csv --customer CUSTOMER --snapshot HASH --mapping FILE --output FILE --json`

Option order is as shown (the existing global JSON/directory options retain their usual handling). Snapshot HASH must equal the current authorized complete statement's `snapshot_hash`; stale or incorrect pins refuse before output. The one-owner SQLite handle remains held through file publication. Current read authority and customer isolation use the existing statement path; filesystem/OS administration remains the trust boundary. Export does not grant access to a revoked reader.

Mapping is strict JSON, at most 64 KiB, with exactly `schema: "ledger-finance-mapping/1"` and `accounts: {party_id: account_label}`. Keys must exactly cover the payer/recipient parties in the exported postings: missing or unused keys refuse. Account labels are nonempty, at most 128 UTF-8 bytes, without control characters. Duplicate JSON keys, unknown properties and invalid JSON refuse. For empty history, explicitly supply an empty accounts object. Labels are operator-supplied references; no tax or chart-of-accounts inference occurs.

## CSV contract

UTF-8 without BOM, comma separators, CRLF row endings. Every cell is double-quoted, with embedded quotes doubled. Fixed header order is declared in `billing/export.rs`. Rows follow retained decision order and each decision's retained posting order. The last row has `row_type=complete`; there are no timestamps generated by exporting. A header-only or missing/truncated trailer is not a complete export.

## High-precision export/3

`ledger-finance-export/3` is selected for an exact `ledger-billing-statement/3`. It keeps the same CSV columns, quoting, mapping input, publication behavior, and reconciliation model. Every posting row and the trailer use USD scale 18. A retained scale-2 amount is converted exactly by multiplying its atoms by `10^16`; a scale-18 amount is unchanged. `record_id`, `record_hash`, receipts, obligations, and retained source bytes still identify the original record. This is an exact unit conversion for the export, not a mutation or rerating of the record. No four-decimal or currency-minor-unit rounding occurs in the export.

The export identity uses version `3` in the canonical digest domain (`billing-finance-csv`). The summary schema is `ledger-finance-export/3`. The original `/2` identity uses digest version `2` and remains unchanged for statement/2. Consumers must compare `(currency, scale, amount_atoms)` together and use exact integer arithmetic with at least the product's 512-bit bound (or arbitrary precision); a converted legacy posting or aggregate may exceed 128 bits. They must not interpret scale-18 atoms as cents.

| Columns | Meaning |
| --- | --- |
| `row_type` | `posting` or final `complete` trailer. Sum only posting rows. |
| `export_id`, `snapshot_hash`, `cutoff` | Logical export identity, pinned verified economic snapshot and total accepted decision count. |
| `posting_count`, `control_net_atoms` | Expected posting count and exact signed control total; repeated metadata, **not amounts to sum per row**. |
| `record_id`, `record_hash` | Original retained posting/action identity and canonical content hash. |
| `receipt_id`, `decision_ordinal`, `target_id`, `event_id` | Original decision/acceptance receipt, local retained ordinal, original work target and posting event. |
| `obligation_id` | Original retained obligation. For a base posting, joined from the retained obligation with the same agreement, book, currency/scale and roles; never minted by export. |
| `reverses_record_id`, `claim_id`, `revision_id` | Existing correction/claim references, empty where absent. An inverse references the exact posting it negates. |
| `tenant_text`, `environment_text`, `agreement_text`, `binding_text` | Existing scope and accepted terms identifiers, encoded as described below. |
| `source_text`, `external_id_text` | Original retained delivery identifiers, not later alias deliveries. |
| `payer_text`, `recipient_text` | Existing obligation parties; signs do not swap these roles. |
| `payer_account_text`, `recipient_account_text` | Explicit supplied mapping values for those parties. |
| `currency`, `scale`, `direction`, `amount_atoms` | For export/2, USD scale 2; for export/3, USD scale 18. Direction is `increase`/`decrease`/`zero`; amount is an exact signed integer string at the declared scale. Positive increases the existing payer→recipient obligation; negative reduces it. These are not invented GL debit/credit rules. |

The complete trailer contains export identity, snapshot, cutoff, posting count/control total and currency/scale. Its posting-specific fields and `amount_atoms` are empty. Empty history produces header plus zero-count, zero-total trailer. Zero-economic decisions can affect cutoff/snapshot without creating a posting row; consult the statement for their receipts.

All `*_text` values carry a mandatory reversible `text:` prefix. Remove exactly that prefix to recover the original identifier/label. This prevents arbitrary text beginning with `=`, `+`, `-`, `@`, whitespace or quotes from becoming a spreadsheet formula, without relying on spreadsheet-specific apostrophe handling. Do not remove the prefix before opening untrusted values in a spreadsheet. Generated canonical IDs and validated numeric fields remain unprefixed. CSV quoting alone is not formula protection. Import money/IDs as text and use exact integer arithmetic; spreadsheets can round large numbers.

## Identities, reconciliation and retries

`export_id` is the core Document-domain canonical digest of `["billing-finance-csv",version,scope,customer,agreement,snapshot_hash,cutoff,accounts]`, with canonical mapping object ordering. Export/2 uses digest version `2`; export/3 uses digest version `3`. Output path, export clock time and formatting of mapping JSON do not enter its identity. It is an export identifier, not a new authoritative ledger record. Identical pinned snapshots/mappings at the same export version produce identical CSV bytes. A new snapshot, changed mapping, or projection version changes export identity.

For deduplication, consumers must explicitly retain `(scope, record_id)` and the posting payload, excluding repeated export-control metadata (`export_id`, `snapshot_hash`, `cutoff`, `posting_count`, and `control_net_atoms`). Repeated unchanged rows may be recognized as duplicates. When upgrading a retained export/2 row to export/3, the same record ID and hash may have a different exact numeric representation: permit only the deterministic conversion from USD scale 2 to scale 18 (`amount_atoms × 10^16`), together with the corresponding `scale` change. Preserve the existing economic posting and update its representation, or compare both after exact normalization to a common scale; do not create or repost a charge. Require the same currency, obligation, roles, account mapping, receipt, event, correction references and other posting data. A changed payload beyond this exact scale conversion requires explicit conflict/reconciliation, never another charge. Across larger snapshots the original record IDs persist. A final filename or export ID alone is not a sufficient incremental posting key.

Reconcile posting-row count and integer sum with the complete trailer and statement. Check exact record IDs, hashes, amounts, receipt membership, obligation and inverse references against the stored statement. Include inverses and replacements separately; do not erase earlier adjustments or sum repeated `control_net_atoms`. `scripts/demo-finance.py` demonstrates the hand-calculated example and explicit consumer behavior. No arbitrary external system's ingestion or deduplication is claimed.

## File publication and failure

The entire verified CSV is prepared before output. A private 0600 temporary file in the existing output directory is created exclusively, written and synced. A same-directory hard link publishes the complete inode at a new destination without replacing any existing file, directory or symlink. The parent directory is synced before success. Existing path components containing symlinks refuse. Use operator-controlled local storage supporting this protocol; no remote filesystem durability promise is made.

Ordinary staging/write/sync/link failures return nonzero with `complete:false`; a partial staging file is cleaned up where possible and never acknowledged as an exported CSV. If parent sync fails after linking, a complete destination may exist although the command reports failure. A killed process may leave an ignored `.ledger-finance-*.tmp` file. Inspect/reconcile using the pinned snapshot; retry to a new destination. Never delete an existing destination automatically and never treat export failure as billing rollback. A lost success response likewise requires inspecting the existing file or retrying to another path.

Local file creation is not downstream ingestion, acknowledgment, payment, a backup or proof against later file modification. CSV export reads may cause normal SQLite sidecar/lock activity, but append no economic records or permission changes. The existing admission bounds remain; users provide RAM, disk and operational headroom. There is no resource reservation or completion guarantee. The owner's waiver of separate independent review and the other deferrals are stated in [CURRENT-REQUIREMENTS.md](../CURRENT-REQUIREMENTS.md).
